# Состояние списка

```ts
interface DataSourceState {
  page: number
  perPage: number
  sort: { key: string, dir: 'asc' | 'desc' } | null
  filters: Record<string, FilterValue>
  search: string
}
```

Состояние живёт в одном месте и правится точечно (`setPage`, `setSort`, `setFilter`, …). Прочитать
его целиком можно через `state`, но менять напрямую нельзя: правки проходят нормализацию, и без неё
появляются баги ниже.

## Смена фильтра возвращает на первую страницу

Отфильтровал список, стоя на пятой странице, — и попал на пустую: результатов оказалось на две.
Выглядит это как «ничего не нашлось», хотя нашлось.

Поэтому страницу сбрасывают **фильтры, поиск и размер страницы**. Сортировка — нет: набор тот же,
изменился только порядок, и пятая страница остаётся осмысленной.

Явная страница в той же правке сильнее сброса: `setPage` после `setFilter` делает ровно то, что
написано.

## Пустой фильтр — это отсутствие фильтра

Снятый фильтр приходит четырьмя видами — `undefined`, `null`, `''` и `[]`, — и все они значат одно.
Сравнивай их по значению, и очистка поля дважды подряд слала бы второй запрос за тем же ответом.

## Правка, ничего не изменившая, запроса не шлёт

Выбрали ту же роль повторно, вернулись на ту же страницу — состояние равно прежнему, и на сервер
идти незачем. Сравнение идёт по значению, включая содержимое фильтров.

## Дебаунс: что откладывается, а что нет

Правка **поиска и фильтров** откладывается (по умолчанию 300 мс) и схлопывается в один запрос: их
набирают. Клик по **странице и сортировке** уходит сразу: это разовое действие, и задержка на нём
читается как подвисание.

`debounce: 0` выключает откладывание совсем.

## Клиентская стратегия

Без `fetcher`, но с `rows` весь набор лежит в памяти, а фильтр, порядок и срез считаются на месте.
Умолчания намеренно простые:

| | Что делает | Чем заменить |
| --- | --- | --- |
| поиск | подстрока по текстовым и числовым полям строки | `match(row, search)` |
| фильтр | равенство по имени поля; список — вхождение | `filter(row, filters)` |
| порядок | сравнение значений поля `sort.key` | `compare(a, b, sort)` |

`rows` может быть `ref` или геттером: набор вправе приехать позже.

## Как это подключается к компонентам

Основной способ — писуемые ссылки под `v-model`: `page`, `perPage`, `sortKey`, `sortDir`, `search`.
Они длиннее спреда ровно на имена пропов, зато их видит `vue-tsc`.

Объекты `table` и `pagination` отдают то же самое одним значением, но `v-bind`-спред строгая проверка
шаблонов в обязательные пропсы не засчитывает: `<GrPagination v-bind="pagination" />` для неё —
компонент без `page`, `pageSize` и `total`. В проекте без проверки шаблонов это самый короткий путь,
в проекте с проверкой — берите ссылки.
