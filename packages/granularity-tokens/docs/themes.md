# Темы

Тема — дизайн-язык целиком: примитивы (скругления, шрифты, отступы), роли каждого режима и
производные состояния. Режим — вариант внутри темы: `light`, `dark` или свой. Тема выбирается на
сборке приложения, режим переключается в рантайме — об этом [`modes.md`](../../granularity/docs/modes.md)
ядра.

Здесь: что тема обязана объявить, какие роли где применяются и на чём уже ломались, как собрать
свой режим или свою тему и что проверить перед выкладкой.

Смежное: [`tokens.md`](./tokens.md) — полная таблица глобальных токенов со значениями каждой пары
«тема × режим»; [`themes/README.md`](../themes/README.md) — каталог и раскладка папки темы;
[`tokens.md`](../../granularity/docs/tokens.md) ядра — покомпонентные токены.

## Что такое тема в терминах пакета

Тема — это **набор семантических ролей** (`--gr-bg`, `--gr-primary`, `--gr-danger-text`, …) в
каждом режиме плюс примитивы, общие для всех режимов:

- **примитивы** (`--gr-space-*`, `--gr-radius-*`, `--gr-text-*`, `--gr-z-*`) от режима не зависят и
  лежат в `root.json` темы — это не «тёмная версия отступа»;
- **роли** — в `modes/<режим>.json`: меняются при переключении режима;
- **производные состояния** (`--gr-primary-hover`, `--gr-danger-active`, …) тема не объявляет: они
  выведены формулой `color-mix` от ролей и подстроятся сами, как только вы поменяете базовую роль.

Практическое правило: меняется при переключении режима → роль; одинаково всегда → примитив.

## Каталог и выбор темы

Встроенные темы — каталог `grThemeCatalog`: id, название, режимы, ссылка на дизайн-систему. Тема
выбирается в конфиге granum — `theme: 'slate'`; в CSS приложения едет одна активная тема. Режимы
переключаются парой `data-theme="<тема>-<режим>"`, режим по умолчанию висит ещё и на `:root`.

**Превью** — другие темы рядом с активной: `previews: ['clay']` в конфиге granum собирает полные
блоки их пар (`[data-theme="clay-dark"]`) с токенами компонентов, но под `:root` превью не выходит
никогда. Поддерево включает его `<GrConfigProvider theme="clay" mode="dark">`. Каждая тема превью
добавляет к CSS свой вес — для приложений это инструмент показа (дизайн-система, портал), а не
переключатель тем.

## Минимальный скелет

Режим `ocean` темы `slate` в CSS — блок под своей парой (собирать его руками не
нужно: см. «Свой режим» ниже):

```css
[data-theme="slate-ocean"] {
  /* Surface roles */
  --gr-bg: #071b2b;
  --gr-fg: #e6f2fb;
  --gr-card: #0d2b42;
  --gr-card-fg: #e6f2fb;
  /* … остальные роли … */
}
```

Полный список ролей, которые обязана объявить тема, — в [`tokens.md`](./tokens.md),
раздел «Роли по режимам». Он генерируется из данных пакета, поэтому не устаревает.

Тот же список доступен программно — удобно, чтобы не сверять глазами:

```ts
import { grRoleTokens } from '@feugene/granularity-tokens'

// имена всех ролей, которые ожидает пакет
const required = grRoleTokens.map(token => token.name)
```

## Суффиксы ролей: где какой цвет применяется

Самая частая ошибка кастомной темы — перепутать роли и получить нечитаемый
текст. У цветных ролей четыре разновидности, и они **не** взаимозаменяемы:

| Суффикс | Что это | Где применяется | Требование к контрасту |
| --- | --- | --- | --- |
| без суффикса (`--gr-success`) | насыщенная заливка | фон бейджа, индикатора, граница | ≥ 3:1 к фону страницы (как граница/индикатор) |
| `-fg` (`--gr-success-fg`) | текст **на** сплошной заливке тоном | подпись бейджа | ≥ 4.5:1 к своей заливке — и к её hover/active |
| `-solid` (`--gr-success-solid`) | заливка кнопочного веса + `-solid-hover`/`-active` | фон solid-кнопки | ≥ 4.5:1 к своему `-solid-fg` |
| `-solid-fg` (`--gr-success-solid-fg`) | текст на `-solid`-заливке | подпись solid-кнопки | ≥ 4.5:1 к `-solid` и к его hover/active |
| `-light` (`--gr-success-light`) | мягкая тонированная подложка | soft-бейдж, алерт, подсветка строки | ≥ 3:1 к тексту, который на ней лежит |
| `-text` (`--gr-success-text`) | текст **на** мягкой подложке или на фоне страницы | текст алерта, soft-бейдж, тональная ссылка, значение статистики | ≥ 4.5:1 к `-light` и к фону страницы |

Отдельно стоят роли состояний, у которых тона нет: `--gr-disabled-bg/-fg/-brd`
для недоступного контрола и `--gr-invalid-brd/-ring/-text` для не прошедшего
валидацию. По умолчанию `invalid` ссылается на danger-тон, но это именно
ссылка, а не копия: ошибка валидации и декоративный `state="danger"` — разные
сообщения, и тема вправе развести их по цвету, не трогая danger.

`--gr-control-brd` — граница переключаемого контрола в покое: коробка
невыбранного `GrCheckbox`, кружок `GrRadio`, дорожка выключенного `GrSwitch`.
Это не разделитель `--gr-brd`: у такого контрола граница — единственное, по чему
его видно, и WCAG 1.4.11 требует от неё 3:1 к соседним цветам. Своя тема обязана
сохранить 3:1 к `--gr-bg`, `--gr-card` и `--gr-muted` — это проверяет
`controlBoundary.test.ts` пакета токенов.

Ключевое, что стоило пакету отдельной серии починок: **насыщенный тон нельзя
использовать как цвет текста**. Причём это не про один-два «неудачных» тона:
каждому найдётся тема, где он проваливает AA на обычной подложке.

| тон | светлый режим (худший фон) | тёмный режим (худший фон) |
| --- | --- | --- |
| `--gr-primary` | 5.74 | **3.70** |
| `--gr-success` | **2.32** | 5.39 |
| `--gr-warning` | **2.56** | 4.58 |
| `--gr-danger` | **4.41** | **3.74** |
| `--gr-info` | 4.72 | **4.07** |
| `--gr-slate` | 6.92 | **4.04** |
| `--gr-azure` | **4.44** | 4.83 |

Парные `-text` держат AA везде — минимум 5.46. Поэтому правило безусловное:
цвет переднего плана берётся из `-text`, а тон остаётся заливкой, рамкой и
индикатором.

Держат его два гейта. Статический — в `defineStyleTokensGate`: он ловит
`text-[var(--gr-<тон>)]` в исходниках любого пакета и предупреждает о
подмешанном тоне (`color-mix` в `text-*`), где долю статикой не оценить.
Второй, `src/__tests__/toneContrast.test.ts` пакета токенов, стережёт сам список: считает
контраст по токенам обоих режимов и требует, чтобы каждый запрещённый тон был
провален по факту, а его парная роль — нет. Без второго список протух бы при
первой перекраске темы, и запрет превратился бы в суеверие.

Симметрично: `-fg` не обязан быть белым. У светлой заливки он обязан быть
тёмным — белый на зелёной заливке даёт 2.5:1.

### Зачем `-solid` рядом с обычным тоном

Пара ролей нужна затем, что у заливки два разных применения с разными порогами.
Бейджу и индикатору хватает 3:1 к фону страницы, и текст на них тёмный (`-fg`).
Solid-кнопке нужен светлый текст, а под него заливка обязана быть темнее: белый
на светлом `--gr-success` даёт 2.54:1. Отсюда `-solid` — тон кнопочного веса со
своим `-solid-fg`.

Второе, менее очевидное: **кнопки всех тонов обязаны выглядеть одной семьёй**.
Бледно-зелёная кнопка рядом с тёмно-красной читается как ошибка вёрстки, поэтому
`-solid` выравнивает вес по всем тонам, а не только там, где не хватает
контраста. Там, где глобальный тон уже достаточно тёмен (`primary`, `danger`,
`info`, `slate` в светлом режиме), `-solid` — просто ссылка на него.

Перекрашивая тон, перекрасьте и `-solid`: они не выводятся друг из друга.

## Ловушки, которые уже случались

Список не гипотетический — каждый пункт ломал светлый режим пакета:

1. **Вторичный текст выверен по фону страницы.** `--gr-muted-fg` живёт не на
   `--gr-bg`, а на `--gr-muted` и `--gr-secondary` — в чипах, таблицах, панелях.
   Считайте контраст по **самому тёмному** из фонов, на которых он появляется.
2. **`-fg` проверен только на базовой заливке.** Hover/active уводят заливку
   темнее (примешивая `--gr-fg`), и текст может провалиться именно там.
   Проверяйте все три состояния.
3. **Тон использован как текст на подложке того же тона.** Иконка `success` на
   `--gr-success-light` — 2.2:1. Нужен `-text`.
4. **`opacity` для disabled-состояний.** Прозрачность разбавляет выверенные
   токены текста и роняет контраст. Гасите фоном (`--gr-muted`), а не
   прозрачностью.
5. **Два тона перепутаны на глаз.** Пакет наступил на это сам: `--gr-info` был
   индиго в двух шагах от `--gr-primary` (ΔE 4.3 при пороге заметности 2.3), а
   их текстовые роли совпадали значением полностью — ссылка `tone="info"` и
   ссылка `tone="primary"` красились одинаково. Лечится не подкруткой одной
   роли, а разведением тона целиком: `info` теперь синий, `primary` остался
   индиго. Подбирая свои значения, считайте ΔE между тонами, а не только
   контраст каждого из них по отдельности.
6. **Тень одна на оба режима.** Уровни `--gr-shadow-*` жили общим набором и
   красились полупрозрачным `rgba(15, 23, 42, …)` — тем же цветом, что фон
   тёмного режима. На тёмном фоне такая тень не даёт ничего: поднятая поверхность
   теряет один из двух каналов подъёма и держится на одной светлоте. Отсюда
   жалоба «карточки не отделяются, страница — одно полотно», хотя пара
   `--gr-card`/`--gr-bg` в тёмном режиме разведена **сильнее** светлой (ΔL* 8.4
   против 1.8). Elevation объявляется в каждом режиме отдельно, и в тёмном тень
   чернее и плотнее. Гейт — `src/__tests__/elevationPerMode.test.ts`.
7. **Мягкая подложка тона звучит громче в тёмном режиме.** Один и тот же
   `-light` отходил от карточки в 1,5–2,8 раза сильнее, чем в светлой, а по
   цветности — до четырёх раз: роль `danger` в тёмном режиме кричала там, где в
   светлой шептала. Подбирая `-light`, меряйте не абсолютные значения, а
   **отход от своей поверхности**: у тёмного режима поверхность другая, и равные
   hex'ы равного результата не дают. Полное равенство тоже не цель — на тёмном
   фоне цвет нужен насыщеннее, иначе подложка сереет и тон перестаёт читаться.

8. **Роль, которую «никто не использует».** Поиск по исходникам не доказывает,
   что роль мертва, и на этом уже ошибались при инвентаризации. Потребление
   бывает двух видов, и оба невидимы для `grep`.

   Первый: `validateTheme` выводит тона **из данных** — тоном считается любая
   роль, у которой есть пара `-fg`, — и проверяет их контраст. Так под проверки
   попадают `--gr-sidebar-accent` и `--gr-sidebar-primary`, хотя их имена нигде
   не написаны буквально. Отдельно `--gr-sidebar` перечислен как одна из четырёх
   поверхностей (`--gr-bg`, `--gr-card`, `--gr-popover`, `--gr-sidebar`), против
   которых меряется контраст.

   Второй: `defineTheme` и `createMode` падают, если тема не задала **любую** объявленную роль.
   То есть роль обязательна по контракту независимо от того, читает ли её хоть
   один компонент, и её удаление ломает каждую собранную потребителем тему.

   Остаток после обеих поправок — не «мёртвые», а **невостребованные компонентами**
   роли: `--gr-input` и `--gr-sidebar-ring` обязаны быть в теме, но ни одна рамка
   их не рисует (`GrInput` стоит на `--gr-brd`). Пришли они из первого коммита
   вместе с остальным словарём shadcn/ui (`--input`, `--ring`, `--popover`,
   `--card`, семёрка `--sidebar-*`), который лёг рядом с собственным
   пространством пакета, а миграция в `--gr-*` перенесла их как есть. Прежде чем
   удалять такую роль, решите, что честнее: подключить её к компоненту или
   поправить её описание — но помните, что удаление ломающее.

## Свой режим: композиция и сборка

Роль, которую режим не объявил, наследуется **не** от «своей» базы, а из
`:root` — то есть из режима по умолчанию. Тёмный режим с одной забытой ролью
получает светлое пятно, и увидит это не сборка, а пользователь. Отсюда прежняя
цена своей палитры: 90 ролей руками, и ещё раз столько же внимания каждый раз,
когда пакет заводит новую роль.

`@feugene/granularity-tokens/theme` собирает режим из данных пакета. Путей два:
`extendMode` — поверх готового режима, объявляете только отличия; `createMode` —
с нуля, все роли свои (см. «Режим с нуля» ниже).

```ts
// theme.config.ts
import { extendMode, tone } from '@feugene/granularity-tokens/theme'

const surfaces = {
  '--gr-bg': '#041e2b',
  '--gr-fg': '#e8f4fa',
  '--gr-card': '#0a2f42',
}

export const ocean = extendMode({
  name: 'ocean', // пара — slate-ocean
  title: 'Океан',
  base: 'dark', // режим встроенной темы, { theme, mode } своей или другой собранный режим
  tokens: {
    ...surfaces,
    '--gr-primary': '#4fd1e0',
    '--gr-primary-fg': '#041e2b',
    ...tone('azure', '#38bdf8', { base: surfaces }),
  },
  // Покомпонентные токены между режимами не наследуются: заданы — переопределены.
  componentTokens: { '--gr-button-primary-bg': 'var(--gr-primary)' },
})

ocean.definition // вход modes.define granum: extends, colorScheme, только отличия
ocean.tokens // полный набор ролей: своё поверх базы
ocean.css // CSS под парой, включая фолбэк производных для браузеров без color-mix
```

Что это даёт кроме объёма:

- **режим не гниёт.** Роль, добавленная пакетом завтра, приедет из базы при
  следующей сборке. Проверять полноту больше не нужно — она обеспечена
  построением;
- **режим проверяется.** Контраст по WCAG и различимость тонов по ΔE — те самые
  ловушки выше. Не прошло — сборка падает с именем роли и полученным
  отношением. Отключается `validate: false`;
- **база — любой режим любой темы.** `'dark'` встроенной темы,
  `{ theme: brand, mode: 'dark' }` своей темы из `loadTheme`, другой собранный
  режим. Пара и `colorScheme` берутся у базы.

### `tone` — семья ролей из одного цвета

Перекрасив `--gr-success`, вы оставляете `-light`, `-text` и `-solid*` от базы,
и они расходятся с новым тоном (ловушка №3). `tone` выводит семью по правилам из
раздела «Суффиксы ролей» и проверяет каждый порог:

```js
tone('success', '#3ddc97', { base: 'dark' })
// → --gr-success, -fg, -solid, -solid-fg, -light, -text
```

Направление сдвигов берётся из базы: у тёмного режима заливка светлее фона, а
текст на ней тёмный. Порог недостижим — `tone` бросает, а не отдаёт нечитаемое:
серый из середины шкалы тоном не станет, на нём не читается ни один полюс.
`roles: ['fill']` ограничивает вывод, если остальное задаётся руками.

### Режим с нуля

`extendMode` берёт базу, и это удобно ровно до момента, когда база начинает
мешать. Высококонтрастный режим, режим под чужой брендбук, режим для печати — у
них нет ничего общего с палитрой пакета, и любое унаследованное значение в них не
«разумный дефолт», а протечка.

**Не наследовать ни от чего в CSS нельзя.** Режим — это блок объявлений под
парой. Роль, которую блок не объявил, берётся из `:root`, а `:root` — это режим по
умолчанию темы. Независимым режим становится ровно тогда, когда объявляет **все**
роли, и это проверяется на сборке:

```ts
import { createMode, tone } from '@feugene/granularity-tokens/theme'

const surfaces = { '--gr-bg': '#ffffff', '--gr-fg': '#000000', '--gr-card': '#ffffff' }

export const contrast = createMode({
  name: 'contrast',
  colorScheme: 'light',
  tokens: {
    ...surfaces,
    '--gr-card-fg': '#000000',
    // …остальные поверхности, границы, состояния
    ...tone('primary', '#0b3fd4', { base: surfaces }),
    // …остальные тона
  },
})
```

Не хватает роли — сборка падает со списком и объяснением, откуда та придёт, если
её не задать. В granum такой режим всё равно наследует режим темы
(`contrast.definition.extends` — `light`, у тёмного — `dark`): оттуда приходят
токены компонентов, а роли он перекрывает все.

| | `extendMode` | `createMode` |
| --- | --- | --- |
| Незаявленная роль | приходит из выбранной базы | сборка падает со списком |
| Пакет завёл новую роль | приедет сама | режим упадёт на сборке и потребует решения |
| Палитра | частично от базы | целиком своя |
| Когда брать | вариация светлого или тёмного | у режима своя логика цвета |

Оба живут рядом в [`apps/playground-theme`](../../../apps/playground-theme/README.md)
— `ocean` поверх тёмного и высококонтрастный `contrast` с нуля.

### Куда девать результат

В приложении на granum — в конфиг, режимом темы:

```ts
// granum.config.ts
import { contrast, ocean } from './theme.config'

defineGranumConfig({
  // …
  theme: 'slate',
  modes: {
    names: ['light', 'dark', 'ocean', 'contrast'],
    define: { ocean: ocean.definition, contrast: contrast.definition },
  },
})
```

Режим встаёт под свою пару `slate-ocean` и получает токены компонентов от
`extends`. Фолбэки `@supports not (color-mix)` такой режим пока берёт у базы:
у `modes.define` granum нет поля для своих.

Без granum или в браузере (редактор тем, тема из пользовательских настроек) —
готовый CSS режима, рантайм-подпутём, который не тянет справочник токенов:

```ts
import { applyTheme } from '@feugene/granularity-tokens/theme/apply'

const remove = applyTheme(ocean.css, { name: 'ocean' })
```

## Своя тема приложения

Режим — вариант той же дизайн-системы. Тема — другой дизайн-язык: свои примитивы
(скругления, шрифты), свои режимы. Своя тема лежит папкой той же раскладки, что
встроенные (`themes/<id>/` пакета токенов), и объявляет только отличия:

```
src/themes/brand/
  theme.json        # { "id": "brand", "title": "Бренд", "extends": "slate", "modes": [...] }
  root.json         # примитивы: { "gr-radius-md": "10px" }
  modes/light.json  # роли режима: { "gr-primary": "#0f766e" }
  modes/dark.json
```

Собирает её `loadTheme` — тем же `defineTheme`, что встроенные: цепочка тем и
режимов, полнота по реестру, контраст и ΔE в каждом режиме, фолбэки по
фактическим формулам. Неполная тема падает с именем токена и режима.

```ts
// granum.config.ts
import { loadTheme } from '@feugene/granularity-tokens/theme/node'

const brand = loadTheme(new URL('./src/themes/brand/', import.meta.url))

defineGranumConfig({
  // …
  theme: brand, // активная тема — вместо 'slate'
  // или превью рядом с активной: previews: [brand]
})
```

- `brand.extends` — тема каталога в цепочке (`slate`): по ней granum берёт токены
  компонентов, которые компоненты держат только для тем каталога.
- `brand.sources` — прочитанные файлы: правка любого в dev перезапускает конфиг.
- Режим файла может наследовать другой режим той же темы:
  `modes/dim.json` — `{ "extends": "dark", "tokens": { … } }`.

Активная тема у сборки одна. Превью — полные блоки пар `brand-light`/`brand-dark`,
которые включает `<GrConfigProvider theme="brand" mode="dark">`; под `:root` превью
не выходит. Рабочий пример — [`apps/playground-theme`](../../../apps/playground-theme/README.md).

### Пропсы по умолчанию темы

Различия, которые токеном не выразить (вид индикатора загрузки, форма группы
кнопок), тема несёт пропсами по умолчанию:

```json
{ "id": "brand", "componentDefaults": { "GrButton": { "variant": "secondary" } } }
```

Они уезжают в `extensions.granularity` манифеста `virtual:granum/themes`. Приложение
отдаёт манифест плагину режимов — и компоненты берут их без провайдера:

```ts
app.use(granularityThemePlugin, { manifest })
// или initThemeEarly({ manifest }) до app.mount()
```

Порядок слоёв: тема → `createGranularity({ componentDefaults })` приложения →
`GrConfigProvider` → локальный проп. `themeComponentDefaults(manifest)` отдаёт слой
темы явно — например для своего провайдера. У превью своих пропсов по умолчанию
нет: манифест несёт `extensions` только активной темы.

## Проверка перед выкладкой

1. **Полнота.** Ни одна роль из `grRoleTokens` не должна остаться
   неопределённой: пропущенная роль унаследуется из `:root`, то есть из
   светлого режима — в тёмном своём режиме это выглядит как случайное белое
   пятно.

   ```ts
   import { grRoleTokens } from '@feugene/granularity-tokens'

   const declared = new Set(
     [...themeCss.matchAll(/(--gr-[\w-]+)\s*:/g)].map(match => match[1]),
   )
   const missing = grRoleTokens
     .map(token => token.name)
     .filter(name => !declared.has(name))
   ```

2. **Контраст.** Прогоните по таблице суффиксов выше. В самом пакете это
   зафиксировано юнит-тестами (`GrBadge/__tests__/grBadgeContrast.test.ts` ядра
   считает 8 тонов × 2 варианта в каждом режиме каждой темы каталога) и axe-гейтом с включённым правилом
   `color-contrast` — воспроизвести подход в приложении дешевле, чем ловить
   жалобы.

3. **Различимость тонов.** Контраст отвечает на вопрос «читается ли текст», но
   не на вопрос «отличит ли человек `info` от `primary`». Тона стоят рядом — в
   галерее статусов, в ряду кнопок, в списке бейджей, — и два похожих оттенка
   там читаются как один. Порог заметности около ΔE 2.3; в пакете это закрыто
   `src/__tests__/tonePalette.test.ts` пакета токенов, который считает попарные расстояния по
   каждой роли и отдельно запрещает полное совпадение значений. Именно на этом
   попался `info`: его текстовая роль совпадала с `primary` буква в букву.

4. **Обе крайности разом.** Проверяйте тему на плотном экране: таблица + чипы +
   алерт + solid-кнопки на одной странице. Ошибки суффиксов видны именно в
   соседстве, а не на отдельном компоненте.
