# Подсветка: одна палитра, три производителя

Код на одной странице обязан выглядеть одинаково независимо от того, каким из
трёх компонентов показан. Ради этого палитра общая, а производителей у неё три.

## Одиннадцать ролей

`key`, `string`, `number`, `literal`, `punctuation`, `keyword`, `comment`,
`type`, `function`, `variable`, `plain`.

Цветов при этом **семь**, и это дизайн, а не нехватка. Тема даёт восемь хорошо
различимых `-text`-ролей, а роли сведены в смысловые группы:

- **имена объявленного** — ключ, функция, тип: один цвет. `obj.field`,
  `obj.method()` и `Foo` различаются позицией, а не оттенком;
- **значения** — строка, число, литерал: каждому свой;
- **ключевое слово** — акцент; **комментарий** — приглушённо;
- **пунктуация и переменная** — обычный текст.

Совпадения объявлены списком в `grCodeBlockContrast.test.ts`: роль, случайно
совпавшая с чужой, краснеет, пока совпадение не объяснят. Там же проверяется
контраст каждой роли на фоне блока — AA 4.5:1 в обеих темах.

## Контракт — функция, а не библиотека

```ts
type GrCodeTokenizer = (code: string, language: string) => GrCodeLine[] | Promise<GrCodeLine[]>
```

Пакет объявляет **потребность**, а не поставщика — ровно как ядро объявляет
`GranularityI18nAdapter` вместо конкретной i18n-библиотеки. Поэтому `shiki` не
появляется ни в зависимостях пакета, ни в импортах типов: привязки к его мажору
нет, потому что нет самой связи.

Подключить можно Shiki, Prism, серверную подсветку или готовые токены из API.

## Как подсветка доезжает до компонента

Двумя путями, и оба нужны:

```ts
// на приложение — иначе страница с двадцатью блоками требовала бы двадцати пропов
app.provide(GR_CODE_HIGHLIGHTER_KEY, tokenizer)
```

```vue
<!-- точечно: другой движок для одного блока -->
<GrCodeBlock :code="log" :highlighter="ownTokenizer" />
```

Не подключён никто — работает встроенный разбор: JSON и обычный текст, ноль
зависимостей. Это нормальный режим, а не деградация.

## Shiki

```ts
import { createHighlighter } from 'shiki'
import { createShikiTokenizer, GR_CODE_HIGHLIGHTER_KEY } from '@feugene/granularity-code/highlight'

const shiki = await createHighlighter({ langs: ['ts', 'yaml'], themes: [] })

app.provide(GR_CODE_HIGHLIGHTER_KEY, createShikiTokenizer(shiki))
```

Какие грамматики загружены и какой движок регулярок собран — WASM или JS —
решает приложение. Мы не выбираем за него и не тащим грамматик, которых оно не
просило.

**Почему тема-метка.** Токены Shiki несут цвет, а не смысл: семантические
scope'ы доступны только с `includeExplanation`, документированным как дорогой.
Поэтому адаптер отдаёт Shiki тему, где каждой группе scope'ов сопоставлен
служебный цвет-метка, и разбирает цвет обратно в роль. Цвета оттуда на экран не
попадают — красит наш CSS.

**Про границу честно:** переименует Shiki метод `codeToTokensBase` в следующем
мажоре — сломается один файл, `highlight/fromShiki.ts`. Контракт
`GrCodeTokenizer` не сломается никогда, а свой адаптер пишется в пять строк.

## CodeMirror

Редактор красится тем же словарём: `highlight/fromLezer.ts` отдаёт карту тегов
Lezer на классы ролей, а `HighlightStyle` собирается из неё. Готовые темы
CodeMirror не берутся ни в каком виде — они принесли бы свою палитру, и
редактор стал бы единственным элементом страницы, не слушающимся темы
приложения.

Наш стиль объявлен `fallback`, а тема — `Prec.lowest`: это умолчание, которое
тема потребителя из `extensions` обязана перекрывать (`docs/theming.md`).

Цвет самих классов `gr-code-<role>` объявлен обычным CSS в `<style>` редактора.
Утилитой UnoCSS его не задать: классы рождаются в рантайме из тегов Lezer, и в
сканируемых пресетом файлах их нет ни одной строкой — правило просто не
породилось бы.

### Мост встроенного разбора

Грамматика есть не всегда: `language="json"` — это имя, а не грамматика. Чтобы
редактор не оказался одноцветным рядом с `GrCodeBlock`, встроенный разбор
подаётся в CodeMirror **декорациями**: `builtInLineTokenizer(language)` отдаёт
построчный разбор, а плагин раскладывает его роли по диапазонам.

Источник разбора один на всех — `highlight/builtIn.ts`. Им красится блок, им же
серверная разметка редактора, им же мост. Разойдись они — цвет менялся бы в
момент гидрации, и увидеть это можно было бы только глазом; поэтому расхождение
ловит гейт `tokenizerBridge.test.ts`, сверяющий разметку CodeMirror с разбором
строка в строку.

Декорируется **только видимое окно**. Это не оптимизация на будущее, а условие
задачи: пересчёт идёт на каждое нажатие клавиши, и разбор всего документа (плюс
`doc.toString()`, копирующий его целиком) сделал бы цену правки зависящей от
размера файла. С окном она зависит от высоты вьюпорта — три-четыре десятка
строк независимо от того, сто строк в конфиге или сто тысяч. Поэтому же тут нет
ни бюджета, ни порога длины: ограничивать нечего.

Позволяет это **строчная локальность** разбора: JSON внутри токена переноса не
содержит — в строковом литерале он экранирован, — поэтому строку можно разобрать,
ничего не зная о соседях. Язык, которому нужен контекст соседних строк (блочный
комментарий, многострочный литерал), в мост не поместится: ему нужна настоящая
грамматика CodeMirror. Это граница возможностей, а не недоделка.

Мост не ставится, когда грамматика приехала: две подсветки поверх одного текста
дали бы роль, зависящую от порядка расширений.
