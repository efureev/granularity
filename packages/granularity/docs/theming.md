# Кастомные темы

Как собрать собственную тему поверх `@feugene/granularity`: что тема обязана
объявить, как её подключить, что проверить перед выкладкой.

Смежное: [`styling.md`](./styling.md) — слои CSS и порядок импортов;
[`tokens.md`](./tokens.md) — полная таблица токенов с текущими значениями.

## Что такое тема в терминах пакета

Тема — это **набор семантических ролей** (`--gr-bg`, `--gr-primary`,
`--gr-danger-text`, …), объявленных на одном селекторе. Больше ничего:

- **примитивы** (`--gr-space-*`, `--gr-radius-*`, `--gr-text-*`, `--gr-z-*`) от
  темы не зависят и переопределять их темой не нужно — это не «тёмная версия
  отступа»;
- **производные состояния** (`--gr-primary-hover`, `--gr-danger-active`, …)
  тема не объявляет: они выведены формулой `color-mix` от ролей и подстроятся
  сами, как только вы поменяете базовую роль.

Практическое правило: меняется при переключении темы → роль; одинаково всегда →
примитив.

## Минимальный скелет

```css
/* app/styles/theme-ocean.css */
[data-theme='ocean'] {
  /* Surface roles */
  --gr-bg: #071b2b;
  --gr-fg: #e6f2fb;
  --gr-card: #0d2b42;
  --gr-card-fg: #e6f2fb;
  /* … остальные роли … */
}
```

Полный список ролей, которые обязана объявить тема, — в
[`tokens.md`](./tokens.md), раздел «Семантические роли по темам». Он
генерируется из данных пакета, поэтому не устаревает.

Тот же список доступен программно — удобно, чтобы не сверять глазами:

```ts
import { grThemeTokens } from '@feugene/granularity/tokens'

// имена всех ролей, которые ожидает пакет
const required = grThemeTokens.map(token => token.name)
```

## Суффиксы ролей: где какой цвет применяется

Самая частая ошибка кастомной темы — перепутать роли и получить нечитаемый
текст. У цветных ролей четыре разновидности, и они **не** взаимозаменяемы:

| Суффикс | Что это | Где применяется | Требование к контрасту |
| --- | --- | --- | --- |
| без суффикса (`--gr-success`) | насыщенная заливка | фон бейджа, индикатора, граница | ≥ 3:1 к фону страницы (как граница/индикатор) |
| `-fg` (`--gr-success-fg`) | текст **на** сплошной заливке тоном | подпись бейджа | ≥ 4.5:1 к своей заливке — и к её hover/active |
| `-solid` (`--gr-success-solid`) | заливка кнопочного веса + `-solid-hover`/`-active` | фон solid-кнопки | ≥ 4.5:1 к своему `-solid-fg` |
| `-solid-fg` (`--gr-success-solid-fg`) | текст на `-solid`-заливке | подпись solid-кнопки | ≥ 4.5:1 к `-solid` и к его hover/active |
| `-light` (`--gr-success-light`) | мягкая тонированная подложка | soft-бейдж, алерт, подсветка строки | ≥ 3:1 к тексту, который на ней лежит |
| `-text` (`--gr-success-text`) | текст **на** мягкой подложке или на фоне страницы | текст алерта, soft-бейдж, тональная ссылка, значение статистики | ≥ 4.5:1 к `-light` и к фону страницы |

Отдельно стоят роли состояний, у которых тона нет: `--gr-disabled-bg/-fg/-brd`
для недоступного контрола и `--gr-invalid-brd/-ring/-text` для не прошедшего
валидацию. По умолчанию `invalid` ссылается на danger-тон, но это именно
ссылка, а не копия: ошибка валидации и декоративный `state="danger"` — разные
сообщения, и тема вправе развести их по цвету, не трогая danger.

Ключевое, что стоило пакету отдельной серии починок: **насыщенный тон нельзя
использовать как цвет текста**. `--gr-success` на светлом фоне даёт около 2.2:1 —
это провал AA даже для крупного текста. Для текста существует `-text`. Правило
закрыто гейтом у `GrLink` (`GrLink.contrast.test.ts`): он же следит, чтобы новый
тон не завёл себе исключения.

Симметрично: `-fg` не обязан быть белым. У светлой заливки он обязан быть
тёмным — белый на зелёной заливке даёт 2.5:1.

### Зачем `-solid` рядом с обычным тоном

Пара ролей нужна затем, что у заливки два разных применения с разными порогами.
Бейджу и индикатору хватает 3:1 к фону страницы, и текст на них тёмный (`-fg`).
Solid-кнопке нужен светлый текст, а под него заливка обязана быть темнее: белый
на светлом `--gr-success` даёт 2.54:1. Отсюда `-solid` — тон кнопочного веса со
своим `-solid-fg`.

Второе, менее очевидное: **кнопки всех тонов обязаны выглядеть одной семьёй**.
Бледно-зелёная кнопка рядом с тёмно-красной читается как ошибка вёрстки, поэтому
`-solid` выравнивает вес по всем тонам, а не только там, где не хватает
контраста. Там, где глобальный тон уже достаточно тёмен (`primary`, `danger`,
`info`, `slate` в светлой теме), `-solid` — просто ссылка на него.

Перекрашивая тон, перекрасьте и `-solid`: они не выводятся друг из друга.

## Ловушки, которые уже случались

Список не гипотетический — каждый пункт ломал светлую тему пакета:

1. **Вторичный текст выверен по фону страницы.** `--gr-muted-fg` живёт не на
   `--gr-bg`, а на `--gr-muted` и `--gr-secondary` — в чипах, таблицах, панелях.
   Считайте контраст по **самому тёмному** из фонов, на которых он появляется.
2. **`-fg` проверен только на базовой заливке.** Hover/active уводят заливку
   темнее (примешивая `--gr-fg`), и текст может провалиться именно там.
   Проверяйте все три состояния.
3. **Тон использован как текст на подложке того же тона.** Иконка `success` на
   `--gr-success-light` — 2.2:1. Нужен `-text`.
4. **`opacity` для disabled-состояний.** Прозрачность разбавляет выверенные
   токены текста и роняет контраст. Гасите фоном (`--gr-muted`), а не
   прозрачностью.
5. **Два тона перепутаны на глаз.** Пакет наступил на это сам: `--gr-info` был
   индиго в двух шагах от `--gr-primary` (ΔE 4.3 при пороге заметности 2.3), а
   их текстовые роли совпадали значением полностью — ссылка `tone="info"` и
   ссылка `tone="primary"` красились одинаково. Лечится не подкруткой одной
   роли, а разведением тона целиком: `info` теперь синий, `primary` остался
   индиго. Подбирая свои значения, считайте ΔE между тонами, а не только
   контраст каждого из них по отдельности.

## Подключение

### Третья тема: свой CSS-слой приложения

Новая тема — это просто CSS приложения, подключённый после foundation-слоя
пакета:

```ts
// src/main.ts
await import('./reset')
await import('./granularity')          // foundation пакета (tokens + light/dark)
await import('./styles/theme-ocean.css') // тема приложения
await import('./app-styles')
```

Конфликта селекторов нет: `[data-theme='ocean']` и `[data-theme='dark']` никогда
не матчатся одновременно, поэтому порядок важен только для читаемости.

**Чего делать НЕ надо:** пытаться добавить тему через `themes.themeFiles`
пресета. Вопреки тому, что можно предположить по названию, это карта
«имя темы → файл», которая **заменяет** CSS уже существующей темы. Темы
приходят пересечением `themes.names` с тем, что объявил провайдер, — имени
`ocean` там взяться неоткуда.

### Перекрасить встроенную тему

Если тем по-прежнему две, а поменять надо только цвета — вот здесь `themeFiles`
и уместен:

```ts
presetGranularNode({
  providers: [granularityProvider],
  themes: {
    names: ['light', 'dark'],
    themeFiles: {
      // CSS пакета для `dark` не попадёт в сборку — его заменит ваш файл
      dark: fileURLToPath(new URL('./src/styles/dark-rebrand.css', import.meta.url)),
    },
  },
})
```

Проверено сборкой: с таким override встроенные значения тёмной темы из бандла
пропадают целиком, остаётся только ваш файл. Значит он обязан объявлять **все**
роли — см. проверку полноты ниже.

### Точечный override без своего файла

Если нужно поменять две-три роли, целый файл заводить не обязательно:

```ts
presetGranularNode({
  providers: [granularityProvider],
  themes: {
    names: ['light', 'dark'],
    tokenOverrides: {
      dark: { '--gr-primary': '#4fd1e0' },
    },
  },
})
```

Работающий пример — приложение [`apps/playground-theme`](../../../apps/playground-theme/README.md):
тема `ocean` третьим слоем, свой контроллер переключения и автопроверка темы.

## Переключение в рантайме

Канон — атрибут `[data-theme]` на `<html>`:

```ts
document.documentElement.dataset.theme = 'ocean'
```

**Ограничение, о котором надо знать заранее:** `useTheme()` типизирован как
`'light' | 'dark'` и умеет ровно эти две темы — persistence в `localStorage`
(ключ `gr-theme`), синхронизацию между вкладками и слежение за
`prefers-color-scheme`. Третью тему он не переключит: для неё нужен свой
контроллер, который просто пишет `dataset.theme`. Переиспользовать при этом
можно только контракт селектора, не сам композабл.

Если тем ровно две, но с другими цветами, — берите `light`/`dark` как имена и
`useTheme()` работает как есть.

**В SSR состояние темы придётся объявить явно.** `useTheme()` без плагина держит его на
уровне модуля — на сервере это одно состояние на все запросы, и выбор одного пользователя
уехал бы в ответ следующему. Поэтому читать тему на сервере можно как есть, а вот менять —
только с плагином:

```ts
app.use(granularityThemePlugin)
app.use(granularityThemePlugin, { storageKey: 'admin-theme', persist: false })
```

Он же нужен, если на одной странице живут несколько Vue-приложений с независимыми
темами, — и тогда к нему обязателен `target`: корень, в который приложение пишет
свой `data-theme`. Селектор тем атрибутный, поэтому работает от любого контейнера;
без `target` изолируется только состояние, а атрибут все приложения пишут в один
`<html>` — побеждает последний. `target` — геттер, потому что на момент
`app.use(...)` корень ещё не смонтирован:

```ts
app.use(granularityThemePlugin, {
  storageKey: 'admin-theme',
  target: () => document.getElementById('admin-app'),
})
```

О «мигании» темы до гидрации в SSR — [`ssr.md`](./ssr.md#тема-без-мигания).

## Что тема может не покрыть: покомпонентные токены

Кроме глобальных ролей у компонентов есть **свои** переменные — ими компонент
перекрашивается и перемеряется точечно. Полный список с природой и значением по
умолчанию — в [`tokens.md`](./tokens.md), раздел «Покомпонентные точки
кастомизации»; источник — `tokens.json` рядом с кодом каждого компонента.
Программно — тем же способом, что и роли:

```ts
import { grComponentTokens } from '@feugene/granularity/tokens'

// всё, чем настраивается дерево
const treeTokens = grComponentTokens.filter(token => token.owner === 'GrTree')
```

Три компонента держат собственный theme-слой поверх глобальных ролей —
`GrButton` (`--gr-button-*`), `GrProgressBar` и `GrImageViewer`. Все три слоя —
ссылки на роли, а не значения: кнопка берёт заливку из `--gr-{tone}-solid`,
прогресс — из тона, просмотрщик — из констант тёмного хрома, одинаковых в обеих
темах по построению.

Практический вывод: чтобы перекрасить кнопки, достаточно объявить в своей теме
`--gr-{tone}-solid` и `-solid-fg` — покомпонентные `--gr-button-*` трогать не
нужно. Они остаются точкой для случая «кнопка обязана отличаться от общей роли».

Остальные покомпонентные токены переопределять не обязательно: у токенов вида
«только хук» есть дефолт из `var(--gr-x, дефолт)`, а `inline`- и `css`-токены
компонент присваивает сам от ступени `size`.

## Проверка перед выкладкой

1. **Полнота.** Ни одна роль из `grThemeTokens` не должна остаться
   неопределённой: пропущенная роль унаследуется из `:root`, то есть из
   светлой темы — в тёмной кастомной теме это выглядит как случайное белое
   пятно.

   ```ts
   import { grThemeTokens } from '@feugene/granularity/tokens'

   const declared = new Set(
     [...themeCss.matchAll(/(--gr-[\w-]+)\s*:/g)].map(match => match[1]),
   )
   const missing = grThemeTokens
     .map(token => token.name)
     .filter(name => !declared.has(name))
   ```

2. **Контраст.** Прогоните по таблице суффиксов выше. В самом пакете это
   зафиксировано юнит-тестами (`GrBadge/__tests__/grBadgeContrast.test.ts`
   считает 8 тонов × 2 варианта × 2 темы) и axe-гейтом с включённым правилом
   `color-contrast` — воспроизвести подход в приложении дешевле, чем ловить
   жалобы.

3. **Различимость тонов.** Контраст отвечает на вопрос «читается ли текст», но
   не на вопрос «отличит ли человек `info` от `primary`». Тона стоят рядом — в
   галерее статусов, в ряду кнопок, в списке бейджей, — и два похожих оттенка
   там читаются как один. Порог заметности около ΔE 2.3; в пакете это закрыто
   `src/__tests__/tonePalette.test.ts`, который считает попарные расстояния по
   каждой роли и отдельно запрещает полное совпадение значений. Именно на этом
   попался `info`: его текстовая роль совпадала с `primary` буква в букву.

4. **Обе крайности разом.** Проверяйте тему на плотном экране: таблица + чипы +
   алерт + solid-кнопки на одной странице. Ошибки суффиксов видны именно в
   соседстве, а не на отдельном компоненте.
