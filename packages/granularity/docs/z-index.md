# Слоирование: z-index и стек оверлеев

Документ описывает **фактическое** состояние слоёв в пакете: шкалу, её
пользователей, отклонения и правила для новых компонентов.

## Шкала

Единственный источник истины — токены в `styles/tokens.css` (генерируются из
`tokens/foundation.json`, группа `Layering: z-index scale`):

| Токен | Значение | Слой |
| --- | --- | --- |
| `--gr-z-dropdown` | `1000` | якорные floating-панели: dropdown, select, tree-select, autocomplete |
| `--gr-z-tooltip` | `1050` | тултипы |
| `--gr-z-modal` | `1100` | модальные окна и диалоги |
| `--gr-z-toast` | `1200` | тосты |

Шаг между слоями — 50: он оставляет место приложению вклиниться между уровнями
(например, свой sticky-хедер под дропдауном), не переопределяя токены пакета.

### Почему floating-панели НИЖЕ модалок

Контринтуитивно, но правильно: поповер, открытый **внутри** модалки, не теряется
под ней, потому что он лежит внутри её stacking-контекста. А поповер, открытый
**снаружи** модалки, перекрывать её не должен — и не перекрывает.

За пределы своего поддерева floating-компоненты не выходят по построению:
панель телепортируется в `body`, но открыта только пока жив триггер, а клик вне
её закрывает (`v-click-outside`).

### Почему тосты выше всего

Тост — уведомление уровня приложения, а не части UI. Он обязан быть виден
поверх открытой модалки, иначе сообщение об ошибке фонового запроса пропадёт.

## Кто какой слой использует

| Компонент | Слой | Как задан |
| --- | --- | --- |
| `GrDropdown`, `GrSelect`, `GrAutocomplete`, `GrTreeSelect` | `--gr-z-dropdown` | `useFloating({ zIndexVar })` |
| `GrTooltip` | `--gr-z-tooltip` | `useFloating({ zIndexVar: '--gr-z-tooltip' })` |
| `GrModal` (и всё, что на нём: `GrDialog`, `GrConfirmDialog`, `GrPromptDialog`, `GrCommandPalette`, `useDialogService`) | `--gr-z-modal` | `grModalStyles.ts`: `fixed inset-0 z-[var(--gr-z-modal)]` |
| `GrToaster` | `--gr-z-toast` | класс `z-[var(--gr-z-toast)]` на контейнере |

`useFloating` принимает `zIndexVar` и подставляет `z-index: var(<token>)` в
инлайн-стиль плавающего элемента. Дефолт — `--gr-z-dropdown`, поэтому новый
якорный компонент попадает в правильный слой без настройки.

## Отклонения (актуально на 2026-07-29)

Не все компоненты сидят на шкале. Это фактическое положение дел, а не
рекомендация:

| Компонент | Значение | Последствие |
| --- | --- | --- |
| `GrDrawer` | `z-50` (литерал) | **ниже всей шкалы**: панель, оставшаяся открытой от dropdown/select (1000), нарисуется поверх выехавшего drawer'а. Практически поймать трудно — панели закрываются по клику вне, — но контракта тут нет |
| `GrImageViewer` | `2000` (константа `DEFAULT_Z_INDEX`, переопределяется пропом `zIndex`) | выше тостов: просмотрщик перекрывает уведомления |
| `GrLoading`, директива `v-loading` | `z-50` в fullscreen-режиме, `z-10` для инлайнового; переопределяется пропом/опцией `zIndex` | fullscreen-оверлей загрузки **ниже всей шкалы**: модалка (1100) закроет его собой. Инлайновый `z-10` вопросов не вызывает — это порядок внутри своего контейнера |

Локальные значения ниже 50 к шкале отношения не имеют: это порядок внутри
собственного stacking-контекста компонента — `z-[1]` у активного сегмента
`GrSegmented` и `GrButtonGroup`, sticky-шапка `GrTable`, `z-0`/`z-10` у
бэкдропа и панели `GrModal`, `z-10` у контента `GrImageViewer`. Их трогать не
нужно.

Отклонения зафиксированы тестом `src/__tests__/layering.test.ts`: список
закрытый, новый компонент с собственным числом в диапазоне страничных
оверлеев (≥ 50) уронит сборку. Если отклонение починили — удалите запись из
теста и из таблицы выше.

## Правила для нового компонента

1. **Якорная панель** (что-то, что позиционируется относительно триггера) —
   `useFloating`, слой не указывать: дефолт уже `--gr-z-dropdown`.
2. **Модальный слой** — строить на `GrModal`, а не на своём `fixed`: вместе со
   слоем достаются esc-стек, top-стек с `inert`, scroll-lock и фокус-ловушка.
3. **Свой `position: fixed` поверх страницы** — только через токен
   (`z-[var(--gr-z-modal)]`), никаких литералов. Нужен новый слой — заводить
   токен в `tokens/foundation.json`, а не число в компоненте.
4. **Порядок внутри компонента** (`z-0`, `z-[1]`, `z-10`) — литералы допустимы,
   пока значение меньше 50: это не глобальный слой. Гейт ловит именно диапазон
   страничных оверлеев.

## Стек оверлеев: не только z-index

Порядок отрисовки — половина задачи. Вторая половина — кто получает Esc и фокус,
когда открыто несколько окон **из разных деревьев рендера** (обычная ситуация:
`useDialogService` монтирует диалог отдельным `render()` в `body`).

HeadlessUI держит собственный стек на каждое дерево, поэтому каждый `<Dialog>`
считает себя верхним. Пакет чинит это двумя общими стеками:

- **`grModalEscStack`** — единый capture-обработчик Esc на `window`. Срабатывает
  раньше обработчиков HeadlessUI, гасит событие
  (`stopImmediatePropagation`) и закрывает **только верхнюю** (последнюю
  зарегистрированную) модалку. Если верхняя открыта с `closeOnEsc: false`,
  событие всё равно не проваливается вниз — иначе Esc закрыл бы нижнее окно.
- **`grModalTopStack`** — вычисление верхнего окна для фокуса. Все нижние
  получают `setTopmost(false)` и помечают свой корень `inert`, освобождая фокус.
  При закрытии верхнего следующее по стеку снова становится верхним.

Практическое следствие: **вложенные диалоги работают** (например, `prompt`
поверх `confirm`) — фокус в поле верхнего не «воруется» нижним окном, а Esc
закрывает именно верхнее.

Оба стека — внутренние; отдельного публичного API у них нет. Компоненту
достаточно строиться на `GrModal`, чтобы попасть в них автоматически.
