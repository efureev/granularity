# Режимы

Какие темы и режимы есть в приложении, решает сборка; какая из них сейчас на странице — рантайм.
Тема пакета по умолчанию — `slate` каталога `@feugene/granularity-tokens`, её режимы — `light` и
`dark`. Тема и режим включаются парой `data-theme="<тема>-<режим>"` на `<html>` или на поддереве;
режим по умолчанию основной темы висит ещё и на `:root`. Классов `.light`/`.dark` нет.

Что такое тема и режим, из чего они состоят и как связаны, — [`concepts.md`](../../granularity-tokens/docs/concepts.md)
пакета токенов; какие роли тема объявляет, как собрать свой режим или свою тему и на каких
ловушках контраста уже ломались, — [`themes.md`](../../granularity-tokens/docs/themes.md). Здесь — всё, что про режимы в приложении: переключение, острова, SSR, свои режимы в
конфиге, несколько тем в одной сборке и токены компонентов по темам.

Смежное: [`styling.md`](./styling.md) — слои CSS и порядок импортов; [`ssr.md`](./ssr.md) — режим
без «мигания»; [`tokens.md`](./tokens.md) — покомпонентные токены ядра.

## Переключение в рантайме

Канон — пара в атрибуте `[data-theme]` на `<html>`; темы сборки, их режимы и пары знает
сборка и отдаёт манифестом `virtual:granum/themes`. `useTheme()` переключает тему и режим поверх
контроллера granum:

```ts
import { initThemeEarly, useTheme } from '@feugene/granularity'
import manifest from 'virtual:granum/themes'

initThemeEarly({ manifest }) // до app.mount()

const { theme, themes, setTheme, mode, modes, isDark, setMode, toggleMode } = useTheme()
setMode('ocean') // режим из modes.define — тем же вызовом
await setTheme('clay') // лист дополнительной темы, затем пара clay-<режим>
```

- `theme` — текущая тема (`ComputedRef`, как `mode`), `themes` — темы сборки в порядке конфига;
  `modes` — режимы текущей темы с `colorScheme` и парами. Это реактивный массив, который
  `setTheme` меняет на месте, поэтому деструктуризация не теряет смену темы.
- `setTheme(id, { mode? })` сначала загружает лист дополнительной темы по адресу из манифеста и
  только потом ставит пару: значения темы без листа были бы чужими. Режим новой темы — заданный,
  иначе одноимённый текущему, иначе первый той же схемы, иначе режим по умолчанию темы.
- `isDark` смотрит на `colorScheme` режима, а не на имя: `ocean` с
  `colorScheme: 'dark'` тёмный.
- `toggleMode()` переключает между первым светлым и первым тёмным режимом текущей темы.
- В хранилище под ключом `gr-theme` (`GR_THEME_STORAGE_KEY`) лежит не пара, а выбор: у основной
  темы — имя режима (`dark`), у дополнительной — `<тема>-<режим>` (`clay-dark`). Режим основной
  темы без её имени переживает смену основной темы на сборке. Сохранённый выбор, которого нет в
  сборке, пропускается — дальше системная схема.
- Пара, уже стоящая на корне (серверный HTML, скрипт в `<head>`), побеждает
  хранилище: контроллер её узнаёт и не перезаписывает.
- Системную `prefers-color-scheme` состояние отслеживает, пока выбор не сохранён,
  и само её не запоминает; другая вкладка, сменившая тему или режим, — тоже применяется.

Без `manifest` действует одна тема каталога по умолчанию — `slate` с режимами
`light`/`dark`: так собран готовый `@feugene/granularity/themes/slate.css` для
подключения без granum. Приложение без granum, взявшее тему по частям
(`themes/slate/root.css` и свои режимы), отдаёт манифест своих режимов —
`createThemeManifest` из `@feugene/granum/runtime`. Приложению на granum с другой темой, несколькими
темами или своими режимами манифест передавать обязательно — пары `slate-*` в его CSS не совпадут ни с одним
селектором.

**Острова — `GrConfigProvider`.** `mode="dark"` ставит пару режима текущей темы на поддерево,
`theme="clay" mode="dark"` — пару другой темы сборки (`data-theme="clay-dark"`). Лист
дополнительной темы остров подгружает сам по адресу из манифеста; странице, которая показывает
тему всегда, лучше импортировать его статически (`virtual:granum/themes/clay.css`) — тогда нет
кадра без значений. Панели оверлеев внутри переносят пару в `body` сами.

**В SSR состояние режима придётся объявить явно.** `useTheme()` без плагина держит его на
уровне модуля — на сервере это одно состояние на все запросы, и выбор одного пользователя
уехал бы в ответ следующему. Поэтому читать режим на сервере можно как есть, а вот менять —
только с плагином:

```ts
app.use(granularityThemePlugin, { manifest })
app.use(granularityThemePlugin, { manifest, storageKey: 'admin-theme', persist: false })
```

Режим запроса плагин принимает `initial`, а хранилище — `storage`
(`createCookieStorage()` granum), чтобы выбор видел сервер.

Он же нужен, если на одной странице живут несколько Vue-приложений с независимыми
режимами, — и тогда к нему обязателен `target`: корень, в который приложение пишет
свою пару. Селектор режима атрибутный, поэтому работает от любого контейнера;
без `target` изолируется только состояние, а атрибут все приложения пишут в один
`<html>` — побеждает последний. `target` — геттер, потому что на момент
`app.use(...)` корень ещё не смонтирован:

```ts
app.use(granularityThemePlugin, {
  manifest,
  storageKey: 'admin-theme',
  target: () => document.getElementById('admin-app'),
})
```

О «мигании» режима до гидрации в SSR — [`ssr.md`](./ssr.md#режим-без-мигания).

## Свои режимы в конфиге

### Режим поверх режима темы

Режимы — у каждой темы сборки свои, в `modes` её записи `themes`. Режим объявляется в
`modes.define` с `extends`: базой станет режим темы целиком, поверх лягут ваши `tokens`, а режим
встанет под свою пару `[data-theme="slate-ocean"]` — с токенами компонентов базового режима:

```ts
defineGranumConfig({
  engine: windEngine(),
  providers: ['@feugene/granularity'],
  themes: [{
    theme: 'slate',
    modes: {
      names: ['light', 'dark', 'ocean'],
      define: {
        ocean: { extends: 'dark', colorScheme: 'dark', tokens: { 'gr-primary': '#0ea5e9' }, title: 'Океан' },
      },
    },
  }],
})
```

Значения можно взять и файлом — `tokensRef` с одним плоским блоком — или собрать
`extendMode` и отдать его `definition` ([«Куда девать результат»](../../granularity-tokens/docs/themes.md#куда-девать-результат)). Режим с именем, которое уже есть у темы, granum
отвергает (`activation-collision`): у каждой пары своё значение.

`engine: windEngine()` здесь и ниже — обязательное поле конфига, а не опция
темы: движок утилит приезжает отдельным пакетом `@feugene/granum-engine-wind`
и выбирается приложением (см. [`installation.md`](./installation.md)). Ключей
`theme`, `modes`, `previews` и `css.previews` верхнего уровня у granum 3.8 нет — конфиг с ними
падает `InvalidConfigError` с подсказкой про `themes` и `activation`.

### Точечный override

Если нужно поменять две-три роли режима, файл заводить не обязательно:

```ts
defineGranumConfig({
  engine: windEngine(),
  providers: ['@feugene/granularity'],
  themes: [{
    theme: 'slate',
    modes: {
      names: ['light', 'dark'],
      // Ключи — без префикса `--`: его добавляет генератор, а ключ с `--`
      // granum отклоняет ошибкой конфига `InvalidConfigError`.
      // Значение ложится в блок пары режима после данных темы и побеждает.
      tokenOverrides: {
        dark: { 'gr-primary': '#4fd1e0' },
      },
    },
  }],
})
```

`tokenOverrides.root` меняет примитивы — то, что одинаково во всех режимах. Правки одной темы
другую не трогают.

### Несколько тем в одной сборке

`themes` перечисляет темы сборки, основная — ровно одна: у списка из одной записи — она, у
нескольких — помеченная `default: true`.

```ts
defineGranumConfig({
  engine: windEngine(),
  providers: ['@feugene/granularity'],
  themes: [
    { theme: 'slate', default: true, modes: ['light', 'dark'] }, // основная
    { theme: 'clay', modes: ['light', 'dark'] }, // дополнительная
  ],
})
```

Основная тема лежит в общем листе `virtual:granum.css` и одна выходит под `:root`. Дополнительная —
своим листом с полными блоками пар: Vite выпускает его ассетом, манифест несёт его адрес, а
`setTheme` и остров `GrConfigProvider theme` грузят лист по нему. Страница, которая показывает тему
всегда, импортирует лист статически — `virtual:granum/themes/clay.css` (одна тема) или
`virtual:granum/themes.css` (все дополнительные). Атрибут и шаблон пары — общие на все темы, в
`activation` конфига.

Работающий пример — приложение [`apps/playground-theme`](../../../apps/playground-theme/README.md):
режимы `ocean` и `contrast`, своя дополнительная тема и автопроверка; рецепты этого раздела
проверяет его `themeRecipes.test.ts`.

## Пропсы по умолчанию темы

Тема несёт пропсы по умолчанию — то, что токеном не выразить (вид индикатора загрузки, форма
группы кнопок): `componentDefaults` в `extensions.granularity` манифеста `virtual:granum/themes`.
Компоненты берут их без провайдера, если манифест отдан `granularityThemePlugin`, `initThemeEarly`
или `useTheme`. Порядок слоёв: тема → `createGranularity({ componentDefaults })` приложения →
`GrConfigProvider` → локальный проп. Слой темы следует текущей теме документа: после `setTheme`
компоненты берут пропсы новой темы. Остров `GrConfigProvider theme="…"` подменяет слой темы
пропсами своей темы. Как тема их объявляет —
[`themes.md`](../../granularity-tokens/docs/themes.md#пропсы-по-умолчанию-темы).

## Токены компонентов по темам

Кроме глобальных ролей у компонентов есть **свои** переменные — ими компонент
перекрашивается и перемеряется точечно. Полный список с природой и значением по
умолчанию — в [`tokens.md`](./tokens.md), раздел «Покомпонентные точки
кастомизации»; источник — `tokens.json` рядом с кодом каждого компонента.
Программно — тем же способом, что и роли:

```ts
import { grComponentTokens } from '@feugene/granularity/tokens'

// всё, чем настраивается дерево
const treeTokens = grComponentTokens.filter(token => token.owner === 'GrTree')
```

Семь компонентов держат значения своих токенов по темам поверх глобальных ролей —
`GrButton` (`--gr-button-*`), `GrBadge` (`--gr-badge-*`), `GrAvatar`, `GrDataTable`,
`GrProgressBar`, `GrImageViewer` и `GrSegmented`: `src/components/GrX/themes/slate/`
с `root.json` (одинаковое во всех режимах) и `modes/<режим>.json`. Почти всё там —
ссылки на роли, а не значения: кнопка берёт заливку из `--gr-{tone}-solid`, бейдж —
из `-solid` в светлом режиме и из роли тона в тёмном, прогресс — из тона,
просмотрщик — из констант тёмного хрома, одинаковых во всех режимах по построению.
Формула со ссылкой `var()` объявляется на каждом `[data-theme]`, поэтому остров
режима пересчитывает её от своих ролей.

Слой бейджа существует ровно затем, что **нужный вес заливки у режимов разный**.
В светлом режиме `--gr-{tone}` — это заливка под тёмный текст, и filled-бейдж читался
тяжёлой почти чёрной плашкой; в тёмном пастельная заливка с тёмным текстом —
штатная конвенция и выглядит верно. Отсюда матрица весов:

| Что | Заливка | Текст | Порог |
| --- | --- | --- | --- |
| solid-кнопка (любой режим) | `--gr-{tone}-solid` | `-solid-fg` | 4.5:1 к своей заливке |
| filled-бейдж, светлый режим | `--gr-{tone}-solid` | `-solid-fg` | 4.5:1 |
| filled-бейдж, тёмный режим | `--gr-{tone}` | `-fg` | 4.5:1 |
| soft-бейдж, алерт | `--gr-{tone}-light` | `-text` | 4.5:1 к подложке |
| точка и счётчик `GrBadgeWrap` | `--gr-{tone}` | `-fg` | 3:1 к фону страницы |
| индикатор, рамка, полоса прогресса | `--gr-{tone}` | — | 3:1 к фону страницы |

Последние две строки — не исключение из первой, а другой вопрос: метка поверх
аватара обязана быть заметна на фоне страницы, а не нести на себе читаемый абзац,
и заливка кнопочного веса читалась бы там второй кнопкой.

Практический вывод: чтобы перекрасить кнопки, достаточно объявить в своей теме
`--gr-{tone}-solid` и `-solid-fg` — покомпонентные `--gr-button-*` трогать не
нужно. Они остаются точкой для случая «кнопка обязана отличаться от общей роли».

Остальные покомпонентные токены переопределять не обязательно: у токенов вида
«только хук» есть дефолт из `var(--gr-x, дефолт)`, а `inline`- и `css`-токены
компонент присваивает сам от ступени `size`.

## Свой CSS под режим

Компоненты переключаются ролями сами. Свой CSS приложения, который в тёмном виде выглядит иначе,
выбирает средство в таком порядке — от того, что ничего не знает ни о теме, ни о режиме, к тому,
что знает о них всё:

1. **Роли `--gr-*`** и формулы от них — `color-mix(in srgb, var(--gr-fg) 8%, transparent)`. Меняются
   с режимом сами и правильно работают во вложенных островах. Покрывают почти всё.
2. **Вариант `dark:` в разметке** — `dark:bg-…`, `dark:hidden`. granum строит его по схеме режимов
   сборки: в него входят все режимы с `colorScheme: 'dark'` всех тем сборки, свои (`ocean`) тоже.
3. **`light-dark(светлое, тёмное)`** в своём CSS. Сборка объявляет `color-scheme` в блоке каждого
   режима, и функция выбирает значение по схеме ближайшего режима — в том числе в острове. Только
   цвета; браузеры с 2024 года (Chrome 123, Firefox 120, Safari 17.5), фолбэка для более старых нет.
4. **Суффикс пары** — `[data-theme$='-dark']`: по имени режима, от темы не зависит. Однозначен,
   потому что в имени режима нет дефиса. Не видит тёмные режимы с другим именем и ломается, если
   приложение сменило шаблон пары (`activation.value`).
5. **Пара** — `[data-theme='slate-dark']`: только для правки, которая действительно относится к
   одной теме.

```css
.hero {
  /* цвет — ролью или light-dark() */
  background: light-dark(#f8fafc, #0b1120);
}

/* не цвет — суффиксом пары */
[data-theme$='-dark'] .hero__art {
  display: none;
}
```

**Вложенные острова.** Селектор предка — `dark:`, суффикс, пара — совпадает и внутри светлого
острова на тёмной странице: тёмный предок остаётся предком. Роли и `light-dark()` этой ловушки не
знают — значение берётся у ближайшего режима. Своему CSS, который обязан уважать острова, — они.

## Проп `dark` у `GrBadge` и `GrChip` — не режим

`<GrBadge dark>` и `<GrChip dark>` — тёмная **плашка** (заливка вместо мягкой подложки), а не
тёмный режим: в светлом режиме она остаётся плотной меткой на светлой странице. Остров тёмного
режима — `<GrConfigProvider mode="dark">`.
