# Вес разметки: вид повторяющегося компонента — лист по атрибутам

Утилиты хороши, пока компонент на странице один. Кнопок, чекбоксов, бейджей и строк
таблицы на странице десятки, и строка классов каждого экземпляра повторяется в HTML
целиком: в ответе сервера, в разметке для гидрации, в памяти DOM. Документ описывает,
когда вид компонента переносится из утилит в его собственный лист и как это делается
без изменения вида и поведения.

## Принцип

**Экземпляр несёт состояние, а не вид.** Вес, тон, ступень и флаги компонент ставит
атрибутами `data-gr-*`. Цвета, размеры и движение задают правила `<style>` компонента
по этим атрибутам. Лист один на приложение и кешируется, разметка экземпляра — десятки
символов.

Образец — `GrButton`:

```html
<!-- атрибуты экземпляра: ~100 символов -->
<button data-gr-button data-gr-variant="primary" data-gr-tone="primary" data-gr-size="md" type="button">…</button>
```

| `GrButton` | Утилитами (3.2.2) | Листом (3.3.0) |
| --- | --- | --- |
| HTML кнопки по умолчанию | ~1 800 символов | ~210 символов |
| CSS кнопки в приложении (утилиты + лист) | 59,0 КБ, gz 5,5 КБ | 20,6 КБ, gz 3,1 КБ |
| JS-модуль стилей в `dist` | 21,5 КБ | 0,9 КБ |
| Safelist | все сочетания веса, тона и ступени | пуст |

CSS уменьшился тоже: утилита с произвольным значением — отдельное правило с экранированным
селектором на каждое сочетание, а лист описывает то же сочетание один раз.

## Когда переносить

Переносить, если выполнены оба условия:

- **компонент повторяется**: десятки экземпляров на странице — кнопки, контролы формы,
  бейджи, вкладки, пункты пагинации, ячейки таблицы;
- **вид — десятки утилит на экземпляр**, у большинства значение произвольное
  (`bg-[var(--gr-…)]`, `hover:…`, `data-[…]:…`). Такие утилиты длинные, и каждая
  повторяется на каждом экземпляре.

Не переносить:

- **одиночный компонент** — окно, панель, сайдбар. Строка классов у него одна на страницу,
  а лист приедет в CSS приложения целиком, со всеми вариантами;
- **раскладку контейнера и места стыковки** — `flex`, `gap`, отступы, которые меняет
  слот или приложение. Утилиты там короткие, и потребителю удобнее видеть их в разметке.

## Как устроено

### Атрибуты — словарь состояния

- Состояние с несколькими значениями — атрибут со значением: `data-gr-variant="outline"`,
  `data-gr-size="sm"`.
- Флаг — атрибут без значения, который есть или нет: `data-gr-square`, `data-gr-off`.
  Значение `"false"` не пишется: селектор `[data-gr-off]` совпадёт и с ним.
- **Состояние, которое разметка уже несёт, второй раз не пишется.** `aria-checked`,
  `aria-selected`, `aria-current`, `aria-disabled`, `aria-invalid`, `aria-orientation`
  и `:disabled` есть у контрола ради доступности — лист читает их напрямую
  (`[data-gr-checkbox-indicator]:not([aria-checked='false'])`). Свой атрибут заводится
  только там, где ARIA молчит: ступень, вид, «только для чтения» у роли без
  `aria-readonly`, ошибка, которую группа показывает, но не объявляет.
- Атрибуты собирает одна функция рядом с компонентом (`grButtonLookAttrs` в
  `grButtonStyles.ts`). Ею же пользуется компонент, который рисуется тем же видом:
  `GrRadio` в виде кнопки берёт атрибуты кнопки и получает её лист, `GrChip` берёт у
  `GrBadge` атрибуты палитры, все поля — рамку поля у `GrInput` (`grFieldLookAttrs`,
  [`field.md`](./field.md)). Импорт функции — то ребро зависимости, по которому лист
  соседа приезжает в приложение (`config.dependencies`). Правила, которые читают
  переменные соседа, живут в листе соседа: `granum doctor` считает объявленным только
  своё, и чип, читающий `--gr-badge-tone-*` из своего листа, получил бы
  `token-undefined`. Поэтому цвета чипа рисует лист `GrBadge`, а у `GrChip` остаются
  размеры, интерактив и недоступность.
- Словарь атрибутов — контракт. По нему пишут селекторы тесты и стили приложения, поэтому
  он документируется на странице компонента и меняется как API.

### Лист — в `<style>` компонента

Лист лежит блоком `<style>` в SFC. Сборка кладёт его в `dist/components/<Name>/styles.css`,
granum доставляет его в слой `granum.components` (`ADDING_COMPONENTS.md`, шаг 3).
`scoped` не ставится: хеш привязал бы лист к элементам шаблона самого компонента, а тем же
видом рисуются и чужие элементы (`GrRadio` в виде кнопки).

Утилиты приложения живут в слое `granum.utilities`, который идёт после `granum.components`.
Поэтому класс на экземпляре (`<GrButton class="…">`) перекрывает вид компонента, какой бы
ни была специфичность селектора в листе. Порядок генерации утилит тут ничего не решает.

### Тон — одно правило на тон, вес читает переменные

Утилитами каждое сочетание веса и тона — свой набор классов: пять весов на восемь тонов.
В листе тон раскладывается одним правилом по переменным компонента, и правило веса читает
только их:

```css
[data-gr-button][data-gr-tone='success'] {
  --gr-button-tone-bg: var(--gr-button-success-bg);
  --gr-button-tone-fg: var(--gr-button-success-fg);
  /* … */
}

[data-gr-button][data-gr-tone]:not([data-gr-off])[data-gr-variant='primary'] {
  background-color: var(--gr-button-tone-bg);
  color: var(--gr-button-tone-fg);
}
```

Вместо сорока сочетаний получается восемь правил тона и пять правил веса. Переменные тона —
механика компонента: в `tokens.json` они записываются с `kind: "css"`, а ручкой приложения
не служат — значение, заданное снаружи, кнопка перекроет своим. Приложение переопределяет
токены тона `--gr-button-<тон>-*`, а правило тона читает их по наследованию.

### Состояния — специфичностью, а не порядком классов

- Наведение и нажатие — `:hover`, `:active` и атрибут нажатого переключателя
  (`[data-gr-pressed]`) в одном селекторе. Нажатие стоит ниже по листу при той же
  специфичности и поэтому сильнее наведения.
- Недоступность не перекрывает цвета веса, а снимает их: правила веса написаны с
  `:not([data-gr-off])`, у недоступной кнопки свои правила. Два правила одной
  специфичности, спорящие за `background-color`, давали бы вид, зависящий от порядка в листе.
- Движение (подъём, вдавливание) — внутри `@media (prefers-reduced-motion: no-preference)`.
  Длительности гасит общий блок `base.css` (`motion.md`).

### Переменные компонента — в листе, а не инлайном

Переменные, которые компонент выводит из пропов (`--gr-segmented-min-height` по ступени,
`--gr-switch-track-bg` по состоянию), ставятся правилами листа на его элементе. Инлайн
остаётся только для того, что известно лишь в рантайме: геометрия индикатора,
произвольный цвет потребителя. Такие переменные записываются в `tokens.json` с
`kind: "css"`. Число элементов, известное только в рантайме, — тоже не повод для
инлайна: неявные треки грида (`grid-auto-columns`) считаются так же, как явные.

### Ступень — одно правило, элементы читают её переменные

Ступень задаёт размеры не только корню, но и элементам внутри: коробке чекбокса, бегунку
переключателя, номеру страницы. Правило на каждый элемент каждой ступени повторяет длинный
селектор четыре раза. Вместо этого ступень — одно правило на корне с переменными
`--gr-<имя>-step-*`, а свойства элементов читают их одним правилом на все ступени:

```css
[data-gr-switch][data-gr-size='md'] {
  --gr-switch-step-height: var(--gr-switch-track-height-md);
  --gr-switch-step-icon: 0.75rem;
}

[data-gr-switch][data-gr-size] [data-gr-switch-thumb] {
  width: calc(var(--gr-switch-step-height) - 4px);
  height: calc(var(--gr-switch-step-height) - 4px);
}
```

- Правило, которое читает переменные, сохраняет `[data-gr-size]` без значения. Специфичность
  та же, что у правила конкретной ступени, и спор с соседними правилами листа решается как
  прежде.
- Свойство самого корня без дополнительных условий ступень ставит напрямую: переменная там
  лишняя. Так `gap` корня `GrPagination`. Высота и отступы `GrButton` стоят под
  `:not([data-gr-square])` и в отдельных правилах аддонов, поэтому они тоже идут через
  переменные. Значение, одинаковое на всех ступенях, — объявление на корне, а не переменная
  ступени.
- Ручка приложения читается там же, где и без ступени, а ступень даёт ей запасное значение:
  `var(--gr-button-square-size, var(--gr-button-step-height))`.
- Элемент берёт переменную у ближайшего предка, который её ставит, то есть у корня своего
  экземпляра. Селектор ступени с потомком (`[data-gr-x][data-gr-size='sm'] [child]`)
  совпадает и через внешний экземпляр. Во вложенном экземпляре того же компонента ступень
  решал бы порядок правил в листе, а не ближайший корень.
- Переменные ступени записываются в `tokens.json` с `kind: "css"`.

Окупается это не везде: имя переменной длинное и повторяется на каждой ступени. Выигрыш есть,
когда ступень задаёт значения нескольким элементам с длинными селекторами. Минифицированный
лист `GrSwitch` стал легче на 1,6 КБ, `GrPagination` — на 1 КБ, `GrButton` — на 0,6 КБ. Где на
ступень одно-два коротких правила (`GrBadge`, `GrRadio`, `GrTabs`), переменные лист утяжеляют, а
у `GrCheckbox` и `GrChip` выигрыш в пару сотен байт не стоит новых записей реестра. Там остаётся
правило на ступень. Решает замер минифицированного листа до и после. gzip повторы
сжимает и сам, поэтому сжатый вес от приёма почти не меняется.

### Шаблон — меньше якорей

Ложная ветка `v-if` оставляет в разметке комментарий `<!--v-if-->`, а у компонента, которого
на странице десятки, их тоже десятки. Необязательные части группируются под общий
`<template v-if>`: у кнопки пять якорей стали двумя.

## Кто уже на листе

`GrButton` (и `GrRadio` в виде кнопки), `GrBadge`, `GrChip`, `GrCheckbox`, `GrSwitch`,
`GrRadio`, `GrTabs`, `GrPagination`, `GrSegmented`. Рамка поля — общий лист `GrInput` для
`GrInput`, `GrTextarea`, `GrNumberInput`, `GrSelect`, `GrAutocomplete`, `GrInputTag`,
`GrTreeSelect`, триггера `GrColorPicker` и полей спутников ([`field.md`](./field.md)).
В спутниках — день и период `GrCalendar` и значение в колонке `GrTimePicker`
(`granularity-chrono`): разметка месяца стала легче на 70 %.

## Как проверить, что вид не изменился

1. **Сверка вычисленных стилей до и после.** Матрица состояний компонента (темы, режимы,
   веса, тона, ступени, наведение, нажатие, фокус, недоступность, загрузка, вложение в
   группы) рендерится в браузере. Вычисленные стили каждого элемента сравниваются
   с снимком, снятым до переноса. Совпасть должно всё, а каждое расхождение — получить
   объяснение. У кнопки сверка совпала на 2 640 состояниях и нашла один старый дефект:
   `outline-none` перебивал отступ контура из темы. Перенос — повод найти и такие
   дефекты: у `GrSegmented` утилита `font-[var()]` писала вес в семейство шрифта, а цвет
   недоступного сегмента проигрывал базовому по порядку утилит в собранном CSS.
2. **Тесты читают лист.** `componentSheet` из `@feugene/granularity-test-kit/vue` разбирает `<style>` компонента и
   считает каскад для элемента так же, как браузер: правило применяется, если селектор совпал
   (`element.matches`), а из совпавших выигрывает правило с большей специфичностью, при
   равной — позднее. Тест проверяет, что элемент получает, а не какие классы на нём висят:

   ```ts
   const { look } = componentSheet('GrButton/GrButton.vue')
   expect(look(button, { hover: true })['background-color']).toBe('var(--gr-button-success-bg-hover)')
   ```

   `cascade` отдаёт объявления как написаны (формулы проверяются текстом), `look` —
   с подставленными переменными, которые лист ставит элементу или его предку.
   `:hover` и `:active` достаются и предкам, как в браузере: подпись чекбокса
   откликается за коробку. Вид из нескольких листов — несколько файлов:
   `componentSheet('GrBadge/GrBadge.vue', 'GrChip/GrChip.vue')`.

   На этом же каскаде держатся проверки контраста: подпись против заливки в каждом
   весе, тоне и состоянии, в каждом режиме каждой темы.
3. **Полнота правил тона.** Тест проверяет, что у каждого тона `GR_TONES` есть правило
   со всеми переменными тона. Тон без правила молча рисовался бы прозрачным.
4. **Значения тем.** `themes:values:check` сверяет, что компонент видит в каждом
   контексте темы. Переменные-псевдонимы, которые компонент ставит себе по атрибутам,
   скрипт разворачивает во все их значения из листа: сверка идёт по каждому тону, как
   прежде шла по классу на тон.

Гейты проверяются мутацией: испорченное правило тона обязано
уронить и тест контраста, и сверку значений тем.
