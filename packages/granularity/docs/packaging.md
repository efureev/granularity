# Почему пакет один

Решение: **`@feugene/granularity` не делится на подпакеты** («базовые», «формы», «навигация»). Документ фиксирует, из
чего это следует и при каком условии решение стоит пересматривать.

Вопрос возникает регулярно, потому что каталог витрины разложен по группам (`actions`, `feedback`, `navigation`,
`overlays`, `forms`, `data`, `utilities`), и группы выглядят готовыми границами пакетов. Они ими не являются.

Живая картина графа — страница **Architecture** в витрине; она строит его из того же `config.dependencies` в рантайме.
Цифры ниже сняты на версии `0.16.0`
(67 компонентов, 66 рёбер, DAG глубины 3).

## 1. Таксономия каталога не совпадает с графом

**51 ребро из 66 (77 %) пересекает границы групп витрины.** Раскрой по этим группам дал бы пакеты, зависящие друг от
друга кольцом:

| Ребро                                      | Из группы  | В группу      |
|--------------------------------------------|------------|---------------|
| `GrRadio` рендерит `GrButton`              | forms      | actions       |
| `GrPagination` рендерит `GrSelect`         | navigation | forms         |
| `GrDataTable` рендерит `GrCheckbox`        | data       | forms         |
| `GrCollapse` рендерит `GrCard`             | overlays   | data          |
| `GrTreeSelect` рендерит `GrTree`           | forms      | data          |
| `GrToaster` рендерит `GrButton` и `GrIcon` | feedback   | actions, data |

Группы каталога — это **навигация для читателя**, ответ на «где мне искать компонент для этой задачи». Они и не обязаны
совпадать с тем, кто кого рендерит, и не совпадают.

## 2. Гранулярность уже есть — без раскроя

Всё, что подпакеты обещают потребителю, пакет отдаёт сегодня:

- **94 subpath-экспорта** в `package.json#exports` — компонент импортируется поодиночке
  (`@feugene/granularity/components/GrButton`);
- **отдельная vite-entry на каждый компонент** — свой чанк в `dist`, свой CSS;
- `sideEffects: ["**/*.css"]` — сборщик приложения не тащит неиспользованное;
- **селекция CSS через `@feugene/unocss-preset-granular`**: `components: [...]`
  подмешивает safelist и стили только выбранных компонентов и их графа зависимостей.

Потребитель платит ровно за выбранное. Подпакет не добавил бы к этому ни байта экономии — он лишь переименовал бы уже
существующую границу.

## 3. Ядро не режется

Связи через контекст и композаблы в графе рендера не видны, но существуют:

| Общее                                              | Сколько компонентов использует |
|----------------------------------------------------|--------------------------------|
| `GrConfigProvider` (контекст размеров и дефолтов)  | 55 из 67                       |
| `components/shared/` (шкалы, тона, `optionFilter`) | 60 из 67                       |
| контекст `GrFormField`                             | 16 контролов                   |

Плюс общие `composables/`, `directives/`, `i18n/locales/` и `tokens/`.

Раскрой даёт `core` + N тонких пакетов, каждый с peer-зависимостью на `core`. Цена: N чейнджлогов, N версий, N шагов
релиза и матрица version skew у потребителя, который поставил `forms@0.17` рядом с `core@0.16`. Отдельно —
`granularityProvider`: пресет ждёт **один** реестр компонентов, и после раскроя его пришлось бы собирать обратно из
кусков.

## Когда решение стоит пересмотреть

Один сценарий: **у семейства компонентов появляется тяжёлая внешняя зависимость, не нужная остальным**. Тогда выносится
именно оно, отдельным companion-пакетом — так уже сделан
[`@feugene/granularity-datepicker`](../../granularity-datepicker/). Порядок описан в [
`companion-packages.md`](./companion-packages.md).

Критерий здесь про **зависимость**, а не про тематику: «форм много, вынесем формы» этим критерием не является.

## Чего этот документ не запрещает

У дескриптора пресета есть поле `group`
(`GranularComponentDescriptor.group`) — оно про **чанки сборки**: при заданном
`group` пресет дополнительно сканирует `dist/groups/<group>/shared/`, куда уезжают SFC, общие для нескольких entry одной
группы. К npm-пакетам это отношения не имеет. Пакет поле не использует, и заводить его есть смысл только когда у группы
компонентов появится общий `.vue`; сегодня такого нет.
