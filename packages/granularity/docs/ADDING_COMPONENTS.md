# Как добавлять новый компонент в `packages/granularity/src`

Этот файл описывает процесс добавления нового компонента в пакет `@feugene/granularity`.

## Базовые принципы

- код нового компонента живёт внутри `packages/granularity/src/components/<ComponentName>`;
- источником правды для подключения компонента в granular-механизмы является `config.ts`;
- набор файлов внутри папки компонента **не обязан быть одинаковым** для всех компонентов: добавляйте только то, что действительно нужно;
- реестры пакета — `src/index.ts`, `package.json#exports`, entry в `vite.config.ts`, провайдер — раскладывает генератор `generate:registry` по файловой системе; руками их не правят.

## Когда компонент нужно добавлять сюда

Добавляйте компонент в `packages/granularity/src/components`, если он должен участвовать в одном или нескольких текущих механизмах пакета:

- экспортироваться из `@feugene/granularity` или через отдельный subpath `@feugene/granularity/components/<ComponentName>`;
- участвовать в селекции `components: [...]` приложения и общих реестрах пакета;
- если у компонента есть свой CSS, он уезжает в `dist/components/<Name>/styles.css` и
  импортируется чанком компонента — отдельного subpath на него нет;
- иметь зависимые granular-компоненты, safelist или локальные CSS-файлы, которые учитывает сборка granum.

## Структура папки компонента

```text
src/components/GrButton/
  GrButton.vue        компонент
  index.ts            публичные экспорты
  config.ts           дескриптор granum
  defaults.ts         пропы, которые задают GrConfigProvider и тема
  grButtonStyles.ts   типы веса, тона и ступени, атрибуты вида
  safelist.ts         классы, собираемые в рантайме (у кнопки пуст)
  tokens.json         реестр токенов компонента
  __tests__/
```

| Файл | Когда | Что в нём |
| --- | --- | --- |
| `<Name>.vue` | всегда | SFC. Свой CSS — блоком `<style>`: сборка кладёт его в `dist/components/<Name>/styles.css`, и чанк компонента импортирует его сам |
| `index.ts` | всегда | компонент, `config`, типы, safelist — образец ниже, в шаге 5 |
| `config.ts` | всегда | дескриптор granum (`defineGranumComponent`): `name`, `safelist`, `dependencies`, `dynamicTokens`, `hookTokens` — только хуки чужого реестра, `group` — общий SFC нескольких компонентов |
| `defaults.ts` | у компонента с настраиваемым оформлением | пропы, которые задают глобально `GrConfigProvider` и тема (`componentDefaults`); регистрирует их в `GrComponentDefaultsRegistry` |
| `gr<Name>Styles.ts` | при вычисляемых классах | мапы классов по size, variant, tone и style-функции |
| `safelist.ts` | если классы собираются в рантайме из частей | перечень семейства — той же функцией, что строит класс (см. «Что обязано попасть в safelist») |
| `tokens.json` | если у компонента свои `--gr-*` | реестр токенов: `name`, `kind`, `default`, `description`; у хука с литералом по умолчанию — `literal` |
| `__tests__/` | всегда | тесты компонента; сквозные гейты пакета находят его сами |

**`tokens.json` — имена токенов как контракт компонента.** Каждая своя переменная `--gr-<name>-*`
объявлена здесь, и `kind` говорит, кто задаёт её значение:

| `kind` | Кто задаёт значение | Как компонент читает |
| --- | --- | --- |
| `theme` | каждая тема каталога — раздел `themes/<тема>/components/@feugene/granularity/<Name>/` пакета токенов | `var(--gr-x)` без запасного значения |
| `hook` | приложение в своём CSS или соседний компонент (`GrButtonGroup` гасит хуками углы звеньев); тема — никогда | `var(--gr-x, запасное)`; запасное — токен или литерал механики с причиной `literal` |
| `css` / `inline` | сам компонент — своим CSS или инлайн-стилем | — |

Хуки из `tokens.json` в `config.ts` не дублируются: сборка сама кладёт их в манифест (шаг 4,
«`hookTokens` — свои из `tokens.json`, чужие руками»). Из реестра генерируются
[`tokens.md`](./tokens.md) (`yarn generate:tokens`) и `grComponentTokens` — подпуть
`@feugene/granularity/tokens`.

Вне папки компонента: страница [`docs/components/<Name>.md`](./components.md) и значения токенов
вида `theme` во всех темах каталога — той же правкой.

## Пошаговый чеклист

### 1. Создать папку компонента

Создайте `src/components/<ComponentName>/` и добавьте в неё файлы нового компонента, которые действительно относятся к granular-пакету.

Минимум — `<ComponentName>.vue`, `index.ts`, `config.ts` и `__tests__/`; остальное — по
таблице «Структура папки компонента».

### 2. Вынести локальную utility/style-логику при необходимости

Если компонент использует вычисляемые классы утилит, размеры, варианты или общие style-helper'ы, держите их рядом с компонентом.

Текущие примеры из пакета:

- `GrDialog/grDialogStyles.ts`;
- `GrFormField/grFormFieldStyles.ts`;
- `GrInput/grInputStyles.ts`.

В таких helper-файлах обычно лежат:

- связанные типы;
- utility-классы и токены классов;
- safelist компонента;
- вспомогательные style-функции.

### 3. Определить, нужен ли компоненту свой CSS

Утилиты покрывают почти всё. Свой CSS нужен там, где утилитой не выразить: псевдоэлементы
(`::before` отклика кнопки, `::after` зоны касания), `@media (pointer: coarse)`,
`prefers-reduced-motion`, ключевые кадры. Он пишется блоком `<style>` в SFC: сборка кладёт его в
`dist/components/<ComponentName>/styles.css`, а чанк компонента импортирует файл сам —
подключать его отдельно некому и незачем.

**Компонент выглядит как поле ввода?** Рамку не собирайте ни утилитами, ни своим CSS: поставьте
на элемент рамки атрибуты `grFieldLookAttrs` и объявите `GrInput` в `dependencies` — рамку, её
состояния, отклик и кольцо нарисует общий лист поля ([`field.md`](./field.md)).

Значения в этом CSS — токены, а не литералы. Дизайн-решение — цвет, тень, радиус, длительность —
токен вида `theme` в `tokens.json` со значениями в темах; CSS компонента его только читает.

`cssFiles` в `config.ts` — для CSS-файла рядом с `config.ts`, который склеивается с `<style>`
компонента (первым — объявленный). У компонентов ядра его сейчас нет.

### 4. Создать `config.ts`

`config.ts` — обязательная точка регистрации компонента.

Именно отсюда текущий код получает:

- `name` компонента;
- `safelist`;
- `dependencies` на другие granular-компоненты;
- `cssFiles`, если у компонента есть локальные CSS-файлы;
- `dynamicTokens` — токены, чьё ИМЯ компонент собирает в рантайме;
- `hookTokens` — только хуки ЧУЖОГО компонента, которые он читает (свои приносит сборка из `tokens.json`);
- имя итогового component style asset.

Пример для компонента без собственных CSS-файлов:

```ts
import { defineGranumComponent } from '@feugene/granum/contract'

import { grButtonSafelist } from './safelist'

export const grButtonConfig = defineGranumComponent(import.meta.url, {
  name: 'GrButton',
  safelist: grButtonSafelist,
})
```

#### `dynamicTokens` — если имя токена собирается в рантайме

`var()`, собранный из переменной, статический анализ не находит. Обрезка
токенов (`pruneTokens` в конфиге granum; с granum 3.12 включена по умолчанию)
сочтёт токен ненужным и удалит его объявление — молча: сборка зелёная, `z-index`
разрешается в `unset`, панель уезжает под соседний слой.

Так работают оба композабла слоёв (`composables/internal/overlayStack.ts`):
имя приходит параметром, а `var(--gr-z-dropdown)` в исходниках не встречается
ни разу. Компонент обязан объявить, что он читает:

```ts
export const grPopoverConfig = defineGranumComponent(import.meta.url, {
  name: 'GrPopover',
  dynamicTokens: ['gr-z-dropdown', 'gr-z-modal'],
  safelist: grPopoverSafelist,
})
```

Имена БЕЗ префикса `--`; допускается `*` в конце. Поле про ПОТРЕБЛЕНИЕ, а не
про владение: `GrPopover` объявляет `gr-z-modal`, потому что читает его из
ветки `calc(var(--gr-z-modal) + N)`, хотя владеет им `GrModal`.

Правило простое: **написал `var(` не с литеральным именем внутри — объяви.**
Обратное тоже верно: имя, которое передаёт ПРИЛОЖЕНИЕ (проп `zIndexVar` у
`GrLoading`), объявлять нечего — держать его забота потребителя.

Держит гейт `src/__tests__/dynamicTokens.test.ts`. Что именно читает композабл,
он вычитывает из его кода — ветку `calc(var(--x) + N)` и `??`-дефолт, — а не
берёт из списка имён: список разошёлся бы с кодом молча и продолжал бы требовать
имя, которого никто не читает. Отдельным правилом гейт ловит любой новый
источник сборки `var()`, а посмотреть не смог — падает.

#### `hookTokens` — свои из `tokens.json`, чужие руками

Токен «только хук» (`kind: "hook"` в `tokens.json`) компонент читает через
`var(--gr-x, дефолт)`, и тема его не задаёт: хук — ручка приложения или экземпляра.
Дефолт — ссылка на токен (`var(--gr-x, var(--gr-bg))`) или литерал механики компонента; у
литерала в реестре обязана стоять причина `literal` — гейт `componentTokens` иначе красный. granum с 3.7 называет такой
токен находкой `token-fallback-only` — «всегда рисует запасное значение», обычно
признак переименования, — если дескриптор не объявил его хуком. `doctor` пакета идёт
с `--strict`, а у приложения та же находка вышла бы на каждом компоненте.

Свои хуки объявлять не нужно: `withRegistryHookTokens` из
`@feugene/granularity-test-kit` в `vite.config.ts` пакета берёт их из `tokens.json`
компонента и его группы (`group`) и кладёт в манифест (`tokens.hooks`). Руками
объявляется только то, что компонент читает у ДРУГОГО: хук соседа или токен, который
сосед ставит инлайном.

```ts
export const grXConfig = defineGranumComponent(import.meta.url, {
  name: 'GrX',
  safelist: grXSafelist,
  // Хук соседа, который X читает со своим запасным значением.
  hookTokens: ['--gr-neighbour-offset'],
})
```

Природа в `tokens.json` обязана быть верной: токен, который ничей CSS не присваивает,
— `hook`, а не `css`. Неверная природа выходит той же находкой.

Пример для компонента с зависимостями:

```ts
import { defineGranumComponent } from '@feugene/granum/contract'

import { grDialogSafelist } from './grDialogStyles'

export const grDialogConfig = defineGranumComponent(import.meta.url, {
  name: 'GrDialog',
  dependencies: ['GrButton', 'GrModal'],
  safelist: grDialogSafelist,
})
```

В `dependencies` перечисляются **прямые** соседи, чью разметку компонент
рендерит — статическим импортом SFC, ленивым `import()` или подмешиванием
чужого safelist. Импорт константы, типа или композабла из чужой директории
зависимостью **не** является: объявив его, вы притащите каждому потребителю
весь CSS и safelist донора. Обход чанков компонента на директории соседа
останавливается — классы соседа приходят из его манифеста, только когда сосед
в селекции, а в селекцию он попадает по `dependencies`. Пропущенное ребро
сборка пакета не пропустит: граф по импортам бандла сверяется с объявленным
(`UndeclaredDependencyError`). Транзитивное объявлять не нужно: граф
разворачивает granum по манифесту.

Проверяют двое: `src/__tests__/componentDependencies.test.ts` (от исходников,
ловит и лишнее) и `yarn doctor` (от собранного `dist`, видит рёбра через общий
чанк). Нормативное определение — `docs/SPEC.md` §4.1 в
`@feugene/granum`.

Пример с CSS-файлом рядом с `config.ts` — у компонентов ядра такого сейчас нет, свой CSS
пишется блоком `<style>` (шаг 3):

```ts
export const grXConfig = defineGranumComponent(import.meta.url, {
  name: 'GrX',
  safelist: grXSafelist,
  cssFiles: ['./styles.css'],
})
```

### 5. Создать `index.ts`

`index.ts` нужен для публичного API компонента и его подключения в пакетный entrypoint.

Минимум:

```ts
export { default } from './GrIcon.vue'
export { default as GrIcon } from './GrIcon.vue'
```

Если наружу должны торчать типы, safelist или helper'ы, экспортируйте их здесь же.

### 6. Убедиться, что utility-классы компонента видны экстрактору granum

Классы компонента извлекает сборка пакета: плагин granum прогоняет экстрактор движка по собранным чанкам и кладёт результат в манифест.

Движок сборке задаётся явно — `granumProvider({ provider, engine: windEngine() })` в `vite.config.ts` пакета, — и им же список отфильтрован: токен, для которого у движка правила нет, классом не считается и в манифест не попадает. Отсюда и диалект словаря в манифесте: список классов — факт о конкретной реализации, а не о пакете (см. [`granum.md`](./granum.md#словарь-утилит-диалект-и-отпечаток)).

Практическое правило:

- держите классы утилит в коде компонента или в его `gr<Name>Styles.ts`;
- CSS, который утилитой не выразить, — блоком `<style>` в SFC (шаг 3).

## Что обязательно обновить вне папки компонента

### Реестры — генератором

```bash
yarn workspace @feugene/granularity generate:registry
```

Скрипт `scripts/generate-registry.mjs` находит компонент по признаку
«директория `Gr*` c `index.ts` **и** `config.ts`» и прописывает его сразу в
четыре реестра:

| Реестр | Что появляется |
| --- | --- |
| `src/index.ts` | `export * from './components/GrX'` |
| `package.json#exports` | subpath `./components/GrX` |
| `vite.config.ts` | entry `components/GrX/index` |
| `src/granular-provider/shared.ts` | импорт `grXConfig` + запись в `granularityComponentConfigs` |

Блоки в TS-файлах размечены маркерами `// <granularity:components>`; править
внутри них руками бессмысленно — следующий запуск затрёт. Порядок записей
(регистронезависимый алфавитный) держит генератор.

Имя экспорта конфига обязано выводиться из имени компонента (`GrX` → `grXConfig`),
иначе генератор остановится с ошибкой.

Рассинхрон ловит тест `src/__tests__/registry.generated.test.ts` — он падает и
когда компонент создан без запуска генератора, и когда компонент удалён, а
записи остались.

### Что генератор НЕ делает

- **Значения токенов в темах.** Токен, значение которого — дизайн-решение (цвет, тень, радиус,
  толщина линии, длительность, кегль), — вида `theme`: компонент читает его без запасного
  значения, а значение кладётся во **все темы каталога** пакета токенов, в раздел
  `themes/<тема>/components/@feugene/granularity/<GrX>/` — `root.json` и
  `modes/<режим>.json`, ключи без `--`. Компонент и его значения во всех темах выходят одним
  пушем. Формула со ссылкой `var()`, одинаковая во всех режимах, — в `root.json`: тогда остров
  режима пересчитывает её от своих ролей. `themesDir` у компонентов ядра нет. Полноту по всем
  темам проверяет `catalogThemes.test.ts`, вид токенов в разделах — `componentTokens.test.ts`, а
  значения по контекстам — `themes:values:check`.
- **Ничего для CSS компонента.** И не нужно: `libInjectCss` вписывает
  `import '../styles.css'` внутрь чанка, так что стиль приезжает вместе с
  компонентом. Отдельного subpath на него пакет не публикует — файл без токенов
  и тем подключать нечем.

Из реестра провайдера (`granularityComponentConfigs` в `src/granular-provider/shared.ts`)
`createGranularityProvider()` собирает granum-провайдер пакета: дескрипторы всех компонентов с
их зависимостями, safelist и токенами — из него сборка пишет манифест.

### Страница компонента — той же правкой, не потом

Компонент без страницы не выбрать: чтобы понять, он тут нужен или сосед, придётся
читать его исходник. Поэтому страница заводится вместе с компонентом, а не
«когда устоится API».

1. `docs/components/<ComponentName>.md` — назначение одной фразой, обязательные
   секции `## Когда брать` и `## Когда взять другое`, дальше неочевидные решения
   и их причины. Перечня пропов там быть не должно: он генерируется.
   Жанр и границы — раздел «Страница компонента» в [`components.md`](./components.md),
   процедура написания — `.claude/rules/component-docs.md`.
2. Имя компонента в [`components.md`](./components.md) §«Опубликованные
   компоненты» становится **ссылкой** на эту страницу.
3. Компонент встаёт хотя бы в одну развилку `docs/COMPONENT-MAP.md` в корне
   репозитория — то есть автор проговаривает, чем он отличается от соседей.
   Развилку назвать не получается — вероятно, компонент дублирует существующий,
   и вопрос стоит задать до реализации, а не после.

### Таблица весов — той же правкой

`docs/entry-sizes.md` и блок сводки в `README.md` перечисляют **каждый**
компонент пакета, и оба генерируются:

```bash
yarn build:granularity                                # генератор читает dist
yarn workspace @feugene/granularity sizes:docs
```

Порядок значим: генератор считает по собранному `dist`, поэтому сборка идёт
первой. Руками эти файлы не правят.

Пропустить шаг легко — к обоим файлам автор компонента иначе не притрагивается,
а локальные тесты о них ничего не знают. Цена высокая: гейт `Entry sizes docs
drift` (`yarn sizes:docs --check`) сверяет **состав таблицы и версию в её
шапке**, стоит он в сборочной джобе, то есть срабатывает и на теге. Узнать о
пропуске на публикации, когда тег уже запушен, дороже всего: повторный push того
же тега события не создаёт.

Килобайты гейт не сверяет и не может: `zlib` жмёт один и тот же `dist`
по-разному в разных средах. Свежесть чисел держится версией в шапке — бамп
обязывает перегенерировать. Подробнее про механику — раздел про `sizes:docs`
в [`companion-packages.md`](./companion-packages.md).

### 4. `package` CSS-exports

Foundation публикуется одним файлом — `@feugene/granularity/styles.css`; utility-классы компонентов
собирает движок на стороне приложения.

Поэтому отдельно править общий source-entrypoint для CSS не нужно: foundation собирает сборка пакета, утилиты — движок приложения.

## Как понять, нужны ли `<style>`, `tokens.json` и `safelist.ts`

### Нужен `<style>` в SFC, если:

- есть правило, которое утилитой не выразить: псевдоэлемент, медиазапрос по указателю или
  движению, ключевые кадры;
- вид, который утилитами весит в разметке больше, чем правилами: компонент, которого на
  странице десятки, с десятками утилит на экземпляр. `GrButton` так рисует вес, тон и ступень
  правилами по атрибутам `data-gr-*` — строка классов из полутора-двух тысяч символов на каждую
  кнопку ушла в один лист. Лист лежит в слое `granum.components`, утилиты потребителя — в
  `granum.utilities`, поэтому класс на экземпляре по-прежнему сильнее вида компонента.
  Когда переносить и как проверить — [`markup-weight.md`](./markup-weight.md);
- это правило касается только этого компонента — общее живёт в `src/styles/base.css`.

### Нужен `tokens.json`, если:

- компонент читает или ставит свою переменную `--gr-<name>-*` — каждая обязана быть в реестре,
  иначе красный `componentTokens.test.ts`;
- у переменной верная природа (`kind`): значение темы — `theme`, ручка приложения — `hook`,
  механика самого компонента — `css` или `inline`.

### Нужен `safelist.ts`, если:

- компонент собирает классы в рантайме из частей — шаблонной строкой,
  конкатенацией, `prefix + value`; целиком такого класса нет ни в одной строке
  кода.

Классы, лежащие в коде целыми литералами, safelist не нужен. Если safelist уже
экспортируется из style-helper, отдельный `safelist.ts` не требуется.

### Что обязано попасть в safelist

Только классы, которые компонент собирает в рантайме из частей
(`` `bg-[var(--gr-button-${tone}-bg)]` ``, `'origin-' + side`), — **все значения
семейства**, по всем значениям параметра. Перечислять их удобнее той же функцией,
которой компонент строит класс: так перечень не разойдётся с рантаймом.

Всё, что лежит в коде целым литералом, — в шаблоне и `<script>` `.vue`, в
`.ts`-хелперах компонента, в мапах `Record<Tone, '…'>`, в модулях
`components/shared/` — granum извлекает сам. `granumProvider` на сборке пакета
обходит от входа компонента все импортированные чанки, включая общие
`dist/chunks/*`, и прогоняет экстрактор по каждому; раскладка чанков на это не
влияет. Дублировать такие классы в safelist не нужно: сборка вычистит запись как
уже извлечённую.

До granum правило было обратным — пресет сканировал только
`dist/components/<Name>/**`, и литералы вынесенного в общий чанк хелпера
приходилось дублировать. Отсюда в истории пакета safelist'ы на сотни записей.

**Литерал в `safelist.ts` — ловушка.** `index.ts` компонента реэкспортирует
safelist, модуль лежит в чанке компонента, и экстрактор находит его литералы.
Класс, который компонент на самом деле собирает из частей, а safelist пишет
строкой, попадёт в CSS «случайно» — и пропадёт, как только строку уберут.
Составное семейство перечисляйте вызовом функции, а не копией строк.

Соблюдение проверяет `src/__tests__/safelist.test.ts` — общий для всех пакетов
гейт `defineSafelistGate` из `@feugene/granularity-test-kit`. Запись safelist,
которая лежит целым литералом в коде компонента, он называет лишней. Код
компонента — его файлы и всё, до чего они дотягиваются относительными
импортами, кроме директорий других компонентов: тот же обход, что у сборки.

## Как тестировать новый компонент

Отдельного «стенда нового компонента» заводить не нужно: сквозные гейты в
`src/__tests__/` находят компонент сами, по реестру и по файловой системе.
Красный гейт после `generate:registry` — это и есть список того, что осталось
доделать; сообщение каждого называет, чего именно не хватает.

Руками дописываются только два, и оба — списки, которые вывести неоткуда:

- `componentSize.test.ts` — стенд рендера, если у компонента настраиваемый
  `size` (гейт сам проверяет, что стенд есть);
- `slotContract.test.ts` — доменное имя слота, если оно новое.

Если у компонента есть заметная runtime-логика, добавьте и отдельные component tests рядом с компонентом, как это сделано у `GrModal`, `GrPromptDialog` и `GrSelect`.

## Что проверить перед завершением задачи

1. У компонента есть минимум `config.ts`, `index.ts` и основной `.vue`-файл.
2. Прогнан `yarn generate:registry`, и тест `registry.generated.test.ts` зелёный.
3. `name` в `config.ts` совпадает с ИМЕНЕМ ДИРЕКТОРИИ компонента — из него
   строится scan-glob `dist/components/<name>/**`. Расхождение = классы
   компонента молча не попадают в CSS; ловится `granular doctor --strict`.
4. При необходимости обновлён `packages/granularity/package.json`.
5. Свои переменные `--gr-<name>-*` — в `tokens.json` с верным `kind`; у вида `theme` значения
   лежат во всех темах каталога (`catalogThemes.test.ts`).
5.1. Если компонент собирает имя токена в рантайме (`var(${…})`, свой
   `zIndexVar`) — оно объявлено в `dynamicTokens`. Иначе обрезка токенов у
   потребителя снесёт объявление молча; ловит `src/__tests__/dynamicTokens.test.ts`.
6. Прогнан `yarn test:granularity` целиком: сквозные гейты сами скажут, чего не хватает.
7. Для компонента добавлены все ожидаемые публичные entrypoint'ы и связанные style asset'ы.
7.1. Пакет пересобран и прогнан `yarn workspace @feugene/granularity sizes:docs`:
   новый компонент обязан появиться в `docs/entry-sizes.md` и в блоке сводки
   README. Гейт `Entry sizes docs drift` живёт в сборочной джобе и потому
   срабатывает в том числе на теге — пропуск всплывает уже на публикации.
8. Заведена `docs/components/<ComponentName>.md` с обеими обязательными секциями,
   имя в `components.md` стало ссылкой, компонент стоит в развилке
   `docs/COMPONENT-MAP.md`. Проверяет гейт `src/__tests__/componentDocs.test.ts`.

## Как добавлять директивы

Директивы в пакете живут отдельно от компонентов — в `packages/granularity/src/directives`.

### Минимальная схема

1. Добавьте новый файл `src/directives/<directiveName>.ts`.
2. Если директива зависит от компонентов или их helper'ов, импортируйте их через относительные пути внутри `packages/granularity/src`.
3. Подключите директиву в `src/directives/index.ts`, чтобы она попала в публичный API.
4. Если директива должна быть доступна через отдельный subpath, убедитесь, что `src/directives/index.ts` подключён как entry в `vite.config.ts`, а `packages/granularity/package.json` содержит export `./directives`.

### Практические правила

- общие типы и утилиты переиспользуйте из `packages/granularity/src`, если они уже есть, вместо дублирования логики;
- если директива нужна только внутренним granular-компонентам, всё равно держите её в `src/directives`, а не внутри одной компонентной папки;
- если вместе с директивой появляется новый публичный API, проверьте, что он экспортируется через `src/directives/index.ts` и описан в `packages/granularity/package.json`, когда нужен отдельный subpath;
- если директива должна быть доступна как глобальная шаблонная директива в IDE конечного приложения, обновите `src/directives/globalDirectives.ts` и проверьте, что `src/directives/index.ts` продолжает подключать этот augmentation через `export type {} from './globalDirectives'`.

## Короткий шаблон действий

1. Создать `src/components/<ComponentName>/`.
2. Добавить `<ComponentName>.vue`, `config.ts` и `index.ts`.
3. При необходимости вынести классы в `gr<ComponentName>Styles.ts` и семейства, собираемые в рантайме, — в `safelist.ts`.
4. Свои переменные — в `tokens.json`; значения вида `theme` — во все темы каталога той же правкой. CSS, который утилитой не выразить, — блоком `<style>` в SFC.
5. Прогнать `yarn generate:registry` — он обновит `src/index.ts`, `package.json#exports`, `vite.config.ts` и реестр провайдера. Руками компонент никуда не вписывают.
6. Прогнать `yarn test:granularity` и дописать то, что потребуют гейты: стенд в `componentSize.test.ts`, доменное имя слота в `slotContract.test.ts`, тесты самого компонента.
7. Написать `docs/components/<ComponentName>.md`, сделать имя в `components.md` ссылкой, поставить компонент в развилку `docs/COMPONENT-MAP.md`.
8. Проверить, что новый компонент или директива корректно подключены в публичный API пакета.
