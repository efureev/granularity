# playground-ssr

SSR-стенд к [`packages/granularity/docs/ssr.md`](../../packages/granularity/docs/ssr.md):
живой сервер + тесты, которые проверяют серверный рендер и гидрацию
воспроизведением, а не чтением исходников.

```bash
yarn build:granularity                                  # приложения работают с собранным dist
yarn workspace @feugene/granularity-playground-ssr dev  # http://localhost:5210/
yarn workspace @feugene/granularity-playground-ssr test:run
```

Открыв страницу, смотрите **исходный HTML** (`Ctrl+U`), а не DOM в инспекторе:
инспектор показывает уже гидрированное дерево, и разница как раз потеряется.

## Что здесь есть

| Файл | Назначение |
| --- | --- |
| `server.mjs` | минимальный SSR-сервер: Vite в middleware-режиме + `renderToString`, включая вставку `ssrContext.teleports` в разметку |
| `src/entry-server.ts` | серверная точка входа; возвращает HTML **и** `teleports` |
| `src/entry-client.ts` | гидрация: `createSSRApp().mount()` |
| `src/App.vue` | демо-страница, разбитая по поведению компонентов при SSR |
| `src/ClientOnly.vue` | обход для компонентов, ломающих гидрацию |
| `src/ProblemPage.vue` | те же компоненты **без** обхода — улика для тестов |
| `test/ssr-snapshot.ts` | снимок серверного HTML, снятый в чистом Node |
| `src/__tests__/ssr.test.ts` | что именно приходит с сервера |
| `src/__tests__/hydration.test.ts` | гидрация: страница приложения и страница-улика |

## Главная находка стенда

**Все телепортирующие компоненты пакета ломают гидрацию.** Не только те, у
которых телепорт без гарда (`GrSelect optionsView="panel"`, `GrAutocomplete`,
`GrDropdown`, `GrTreeSelect`), но и «защищённые» через `:disabled="!isClient"`
(`GrTooltip`, `GrModal`, `GrDrawer`, `GrToaster`, `GrImageViewer`).

Причина одна: структура первого клиентского рендера отличается от серверной.
`isClient` вычисляется в `setup`, поэтому на сервере телепорт выключен, а на
клиенте включён сразу — Vue гидрирует, ожидая одно, а находит другое.

Что это даёт на практике (замерено):

- `Hydration node mismatch` в консоли;
- серверная панель остаётся в DOM сиротой — панелей становится две;
- в худшем случае панель «прилипает» к `div#app` и пишет в него
  `position:fixed; display:none` — **страница исчезает целиком**.

Последнее — не гипотеза: демо-страница была пустой, пока проблемные компоненты
не завернули в `ClientOnly`. Подробности и решение — ANALYSIS §60.

**Вставлять `ssrContext.teleports` в разметку всё равно нужно:** без этого
расхождений заметно больше (11 против 4 на демо-странице). Но проблему это не
решает.

## Ловушка, на которой стенд сам чуть не соврал

Первая версия тестов делала `renderToString` **внутри** теста с
`environment: 'jsdom'`. В jsdom `window` существует, поэтому гарды
`typeof window === 'undefined'` считали себя клиентом, и «серверный» HTML
получался таким, какого настоящий сервер никогда не отдаст.

Поэтому серверный рендер вынесен в `test/ssr-snapshot.ts` — `globalSetup`
витеста, который выполняется в чистом Node. Тест гидрации (jsdom) читает уже
готовый снимок. Если будете расширять стенд — не рендерите на сервере из
jsdom-теста.

## Что стенд НЕ покрывает

- потоковый рендер (`renderToWebStream`, `renderToNodeStream`);
- Nuxt-специфику (его собственные `<ClientOnly>`, payload, роутинг);
- production-сборку SSR (`yarn build` собирает клиент и сервер, но отдельного
  prod-сервера здесь нет — для примера достаточно dev).
