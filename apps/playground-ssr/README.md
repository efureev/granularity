# playground-ssr

SSR-стенд к [`packages/granularity/docs/ssr.md`](../../packages/granularity/docs/ssr.md):
живой сервер + тесты, которые проверяют серверный рендер и гидрацию
воспроизведением, а не чтением исходников.

```bash
yarn build:granularity                                  # приложения работают с собранным dist
yarn workspace @feugene/granularity-playground-ssr dev  # http://localhost:5210/
yarn workspace @feugene/granularity-playground-ssr test:run
```

Открыв страницу, смотрите **исходный HTML** (`Ctrl+U`), а не DOM в инспекторе:
инспектор показывает уже гидрированное дерево, и разница как раз потеряется.

## Страницы: два рода, и они не взаимозаменяемы

**Тематические** (`/app`, `/teleport`, `/risky`, `/overlay-stack`, `/chrono`,
`/charts`, `/dashboard`, `/editor`) — фикстуры под класс дефектов. Они держат
то, что видно только в связке нескольких компонентов: механизм проверки часов
подменой заголовка, уникальность `id` масок в SVG, регрессия §60 на дубль
панели, два открытых оверлея и `inert`, утечка темы между запросами. Только они
попадают в шапку стенда.

**Страницы компонентов** (`/c/GrButton`, `/c/GrPagination`, …) — по одному
компоненту на адрес, из реестра фикстур. Отвечают за полноту: каждый компонент
экосистемы поднимается на сервере и гидрируется начисто. Карта — корень `/`.

Изоляция здесь не аккуратность, а условие измерения: на общей странице падение
одного компонента уносит рендер всей, и остальные сто перестают проверяться
разом, а расхождение в общей куче не указывает на виновника.

## Что здесь есть

| Файл | Назначение |
| --- | --- |
| `server.mjs` | минимальный SSR-сервер: Vite в middleware-режиме + `renderToString`, включая вставку `ssrContext.teleports` в разметку |
| `src/entry-server.ts` | серверная точка входа; возвращает HTML **и** `teleports` |
| `src/entry-client.ts` | гидрация: `createSSRApp().mount()` |
| `src/pages.ts` | адреса: тематические страницы + генерация страниц компонентов из реестра фикстур |
| `src/App.vue` | демо-страница, разбитая по поведению компонентов при SSR |
| `src/TeleportPage.vue` | набор из одних телепортирующих компонентов — регрессионный гейт |
| `src/catalog/Catalog.vue` | корень `/`: карта страниц по пакетам |
| `src/catalog/fixtures/` | по фикстуре на компонент; `pages/` — люк в `.vue` для сложных композиций |
| `test/ssr-snapshot.ts` | снимок серверного HTML **всех** страниц, снятый в чистом Node |
| `src/__tests__/ssr.test.ts` | что именно приходит с сервера |
| `src/__tests__/hydration.test.ts` | гидрация тематических страниц |
| `src/__tests__/components.test.ts` | гидрация каждого компонента поодиночке + гейт полноты |

## Как добавить компонент

Строкой в `src/catalog/fixtures/core.ts` (или в файл своего пакета в
`companions.ts`):

```ts
{ name: 'GrX', about: 'что именно рискованно на сервере', render: () => h(GrX, { … }) }
```

Адрес, страница и три проверки — серверный рендер без исключения, непустая
разметка, гидрация без расхождений — появятся сами. Забыть компонент нельзя:
гейт полноты сверяет реестр фикстур с `granular-provider` пакета в обе стороны.

Два правила для фикстуры:

- **никаких часов, случайности и замеров среды.** Иначе сервер и клиент
  разойдутся по вине стенда, а не компонента. Датированному давайте опору
  (`today`, `base`), как это сделано в `companions.ts`;
- **компонент, который на сервер ничего не отдаёт** (закрытый модальный слой),
  помечается `emptyOnServer: true`. Флаг двусторонний: без него гейт требует
  непустую разметку, с ним — пустую. Иначе «страница отрисовалась» зеленело бы
  там, где не приехало ничего, а гидрация сравнивала бы две пустоты.

Композиция, которая в `h()` перестала читаться, — отдельный `.vue` в
`src/catalog/fixtures/pages/` и `page:` вместо `render:`.

## Что этот стенд доказал (и починил)

Стенд создавался, чтобы проверить SSR-контракт из документации. Первый же
прогон показал, что **все телепортирующие компоненты пакета ломали гидрацию** —
не только те, у которых телепорт был без гарда (`GrSelect optionsView="panel"`,
`GrAutocomplete`, `GrDropdown`, `GrTreeSelect`), но и «защищённые» через
`:disabled="!isClient"` (`GrTooltip`, `GrModal`, `GrDrawer`, `GrToaster`,
`GrImageViewer`).

Причина была одна: `isClient` вычислялся в `setup`, поэтому на сервере телепорт
выключался, а на клиенте включался сразу — структура первого клиентского
рендера не совпадала с серверной. Замеренные последствия: `Hydration node
mismatch`, осиротевшая копия панели в DOM и — в живом браузере — панель,
«прилипающая» к `div#app` со своими `position: fixed; display: none`, после
чего **страница исчезала целиком**.

**Починено** (ANALYSIS §60, 2026-07-29): композабл `useTeleportEnabled()`
включает телепорт в `onMounted`, поэтому первый клиентский рендер повторяет
серверный, а панели переезжают в `body` уже после гидрации.

Тесты здесь остались на месте, но с обратными ожиданиями — теперь это
регрессионный гейт: `TeleportPage.vue` (набор из одних телепортирующих
компонентов) обязан гидрироваться начисто, без дублей панелей и с пустым — если
не считать якорей — `ssrContext.teleports`.

## Ловушка, на которой стенд сам чуть не соврал

Первая версия тестов делала `renderToString` **внутри** теста с
`environment: 'jsdom'`. В jsdom `window` существует, поэтому гарды
`typeof window === 'undefined'` считали себя клиентом, и «серверный» HTML
получался таким, какого настоящий сервер никогда не отдаст.

Поэтому серверный рендер вынесен в `test/ssr-snapshot.ts` — `globalSetup`
витеста, который выполняется в чистом Node. Тест гидрации (jsdom) читает уже
готовый снимок. Если будете расширять стенд — не рендерите на сервере из
jsdom-теста.

## Что стенд НЕ покрывает

- потоковый рендер (`renderToWebStream`, `renderToNodeStream`);
- поведение компонента дальше первого рендера: страницы компонентов проверяют
  подъём и гидрацию, а не сценарии. Варианты, состояния и взаимодействие — забота
  витрины и юнит-тестов пакета;
- Nuxt-специфику (его собственные `<ClientOnly>`, payload, роутинг);
- production-сборку SSR (`yarn build` собирает клиент и сервер, но отдельного
  prod-сервера здесь нет — для примера достаточно dev).
